PROJECT
-------
Name: JSimpleList
Package: au.com.jobsheet.jsimplelist
Local project: D:\SimpleList
Public repository: https://github.com/jobsheet-aus/JSimpleList
Purpose: Small local-first native Android list app. Version 2.0 generalises the original fixed To-do and Shopping lists into user-named dynamic lists and adds optional online sync/sharing.
Intrinsic list kinds: TODO, SHOPPING and DISCUSSION. Shopping differs by having a Qty field.
Google Play is the intended public distribution channel.

CORE PRODUCT PRINCIPLES
-----------------------
- Keep JSimpleList deliberately small, direct and local-first.
- Local-only use requires no account and must continue to work without internet or backend availability.
- Signing in must never automatically upload existing local lists.
- A local list becomes online only through an explicit user action for that specific list.
- Online/shared lists remain fully cached in Room and usable offline.
- Preserve local UUIDs as server UUIDs for online-backed lists/items; never create a second identity for the same record.
- List ownership is absolute. The creator remains owner; ownership is not transferred or inherited.
- One authenticated account at a time per Android device is the deliberate UX model.
- Back cancels/closes the most local active operation first.
- Existing-value editing behaviour is field-specific: short replacement-style values such as Qty/default names select all, while item descriptions place the cursor at the end.

2.0 LOCAL DATA MODEL
--------------------
Room schema version 6 contains `lists`, `items` and `list_accounts`.

ListEntity:
- id UUID string
- name user-controlled
- kind TODO / SHOPPING / DISCUSSION
- position persisted list order/cache position
- createdAt
- updatedAt for metadata reconciliation
- onlineState legacy/current-render convenience value LOCAL / ONLINE_OWNER / ONLINE_MEMBER; account-specific authority lives in `list_accounts`

ItemEntity:
- id UUID string
- listId
- description
- quantity nullable; Shopping only
- completed
- position
- createdAt
- updatedAt
- deletedAt nullable tombstone
- createdByUserId / updatedByUserId nullable attribution fields

ListAccountEntity / `list_accounts`:
- composite primary key `(listId, accountId)`
- accountId is authenticated Supabase user UUID
- onlineState is ONLINE_OWNER or ONLINE_MEMBER for that account/list relationship
- the same cached list may legitimately have relationships for multiple accounts on one device
- a genuine device-local list has no `list_accounts` row

Visibility contract:
- signed out: show only genuine local lists
- signed in as account A: show local lists plus online lists related to account A
- another account's cached online lists must not leak into the active account's UI
- `loadVisibleLists(accountId)` projects the active account relationship state into returned lists

Legacy upgrade:
- Legacy 1.1 SharedPreferences JSON imports only when Room has no lists and genuine legacy keys exist.
- Fresh 2.0 install starts with zero lists.
- Genuine upgrade import creates ordinary To-do and Shopping ListEntity rows and preserves descriptions, quantities, completion and order.
- Existing local data migrates safely through Room schema upgrades; tombstones/attribution default safely.
- Legacy JSON remains untouched after import.
- Real Google Play-signed 1.1 -> 2.0 in-place upgrade testing passed on device. Representative To-do/Shopping items, quantities, completed states, ordering and font scale were preserved.

2.0 LIST MODEL / UI
-------------------
- Every list has a user-controlled name independent of kind; names need not be unique because UUID is identity.
- New-list flow: Type -> Name -> Create.
- Defaults: `To-do list`, `Shopping list`, `Discussion points`.
- Zero lists is valid.
- One current list fills the screen; horizontal swipe moves between lists.
- Manage lists is the canonical arbitrary-list navigation/admin surface.
- Online/shared lists show the muted chain/link icon; local lists are unmarked.
- Pull-to-refresh performs online discovery/reconciliation.
- Last active list is persisted/restored safely when still visible.
- Bulk Uncheck all is implemented in the list column-heading row and has conservative Undo.

Item ordering:
- New items insert at the top using persisted position.
- Display respects position/createdAt while presenting incomplete before completed.
- Toggling completion changes completion state, not item position.
- Persisted position remains the foundation for future manual item reordering.

Editing UX:
- Existing items edit inline.
- Item description cursor starts at the end.
- Shopping Qty selects its existing value on focus.
- VersionCode 5 includes the large-text editor improvement: edit text is capped at 22sp, edit fields can grow vertically with `heightIn`, and Shopping Qty width grows with larger text.
- Real-device testing shows the large-text clipping is materially improved.
- Minor unnecessary left padding on the edit-row checkbox remains and is deliberately deferred to 2.1.
- Cancel behaviour is shared by visible Cancel and Android Back.

AUTH / PROFILE
--------------
- `AuthRepository.kt` uses Supabase six-digit email OTP authentication.
- OTP delivery through Supabase Auth -> Resend SMTP -> `jsimplelist@jobsheet.com.au` is proven.
- Session persists across normal app close/reopen.
- Re-authenticating the same email returns the same Supabase user UUID.
- Startup waits for Supabase Auth initialization before reading persisted session.
- supabase-kt remains pinned to 3.2.1 because later tested releases are incompatible with the current Kotlin toolchain.
- `ProfileRepository.kt` stores profiles keyed by auth.users.id.
- Display names are user-chosen, non-unique, trimmed and limited to 1-50 characters.
- Sign out is non-destructive and separate from account deletion.

Current Android account/menu state:
- Existing auth works, but release review on 4 September 2026 identified the discoverability of the sign-in path as inadequate for 2.0.
- A clear, obvious Sign in / Online account entry point is now a 2.0 release requirement.
- Do not change the local-first rule: signing in must still leave local lists local unless the user explicitly makes a list online.
- Signed-out visibility remains local-only; signed-in visibility adds that account's online lists.
- Account deletion remains a separate destructive action.

ONLINE ACCOUNT / OWNERSHIP
--------------------------
- Online identities are persistent Supabase Auth users.
- Shared/online relationships belong to authenticated users; local lists belong to the device.
- Account deletion is implemented through privileged hosted backend logic; no service-role/admin secret ships in Android/browser.
- Android account-deletion cleanup is account-scoped: remove the deleted account's relationships, remove owned online lists, keep genuine local lists and do not convert unrelated online cache rows into local lists.
- Disposable-account end-to-end testing succeeded.
- Owned online/shared lists are destroyed when the owner's account is deleted.
- Non-owner account deletion removes membership but preserves contributed items in another owner's list because those items belong to the list.
- Dormant empty-account auto-purge remains deliberately deferred.

--------------------------
Canonical migrations live under `supabase/migrations` and are applied through `npx supabase ...`.

Important deployed components:

GREEN invitation flow:
- `invite-list` sends a purpose-specific email for GREEN recipients containing one opaque `https://jslist.jobsheet.com.au/invite?h=...` continuation.
- Handoff token is 32 random bytes; only SHA-256 is stored; expiry is 24 hours.
- Passive browser inspect is scanner-safe and grants nothing.
- Explicit `Join list` is the redemption boundary.
- Server bootstraps/redeems the invited Supabase identity and then calls authoritative `accept_list_invitation()`.
- Forwarding the opaque invitation link forwards the short-lived invitation capability; this is an accepted UX/security trade-off.
- Private-browser testing with a never-used email proved the GREEN flow end to end.

Member-join notification fan-out:
- Implemented in migration `20260902120431_notify_all_members_on_join.sql`.
- `notifications.source_invitation_id` is no longer globally unique; uniqueness is `(source_invitation_id, recipient_user_id)`.
- Successful `accept_list_invitation()` creates an `invitation_accepted` notification for every other active list member, excluding the joining member.
- The owner is included naturally through active membership rather than a special owner-only path.
- Notification insertion is non-authoritative/non-blocking: failures raise a warning and must not roll back successful membership acceptance.
- Existing notification trigger feeds the durable push outbox.
- Migration is applied to hosted Supabase. Wider multi-user real-device fan-out testing is deferred until more 2.0 users/devices are available.

Push state:
- FCM invitation, accepted/join and declined pushes work on real Android devices.
- Notification taps route account-safely to relevant invitation/list.
- Durable `push_outbox` and `send-push-outbox` are deployed.
- The removed automatic in-app `Sharing update` notification fallback must not be reintroduced.
- Immediate ACTIVE_ANDROID invitation push is still synchronous inside `invite-list`; durable/non-blocking delivery remains later work.
- KNOWN_USER delayed reminder remains later work.

LIST SYNC / REALTIME
--------------------
- Local lists remain local and are never uploaded merely because the user signs in.
- `discoverOnlineLists()` rebuilds current-account `list_accounts` relationships from authoritative `get_my_online_lists()` results.
- Remote lists import/reconcile into Room cache and authoritative snapshots refresh items.
- Add/edit/tick/untick write Room first then push for online lists.
- Online item deletion uses local/server tombstones.
- Owner Delete remains server-first; member Leave remains server-first; local Delete remains Room-only.
- Per-list private realtime topic: `jsimplelist:list:<list UUID>`.
- Realtime payloads signal `list_changed`; clients load authoritative state rather than trusting payload rows.
- Origin client UUID suppresses own-origin refresh loops.
- Per-list realtime cannot discover unknown list UUIDs; account-level realtime remains future work.
- Failed ordinary online writes retain the Room change; durable retry/reconciliation remains future work.
