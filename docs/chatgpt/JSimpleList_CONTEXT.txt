PROJECT
-------
Name: JSimpleList
Package: au.com.jobsheet.jsimplelist
Local project: D:\simplelist
Public repository: https://github.com/jobsheet-aus/JSimpleList
Purpose: Small local-first native Android list app. Version 2.0 generalises the original fixed To-do and Shopping lists into user-named dynamic lists and adds optional online sync/sharing.
Intrinsic list kinds: TODO, SHOPPING and DISCUSSION. Shopping differs by having a Qty field.
Google Play is the intended public distribution channel.

CORE PRODUCT PRINCIPLES
-----------------------
- Keep JSimpleList deliberately small, direct and local-first.
- Local-only use requires no account and must continue to work without internet or backend availability.
- Signing in must never automatically upload existing local lists.
- A local list becomes online only through an explicit user action for that specific list.
- Online/shared lists remain fully cached in Room and usable offline.
- Use one common list model for household and business/work sharing; do not create a separate team hierarchy unless it becomes genuinely useful.
- Preserve local UUIDs as server UUIDs for online-backed lists/items; never create a second identity for the same record.
- List ownership is absolute. The creator remains owner; ownership is not transferred or inherited.
- Back cancels/closes the most local active operation first. Only when nothing transient is active should Back be allowed to leave JSimpleList.
- Existing-value editing behaviour is field-specific: short replacement-style values such as Qty/default names select all, while item descriptions place the cursor at the end so small wording edits do not risk replacing the whole description.

2.0 LOCAL DATA MODEL
--------------------
Room schema version 4 contains `lists` and `items`.

ListEntity:
- id: UUID string
- name: user-controlled
- kind: TODO / SHOPPING / DISCUSSION
- position: explicit persisted per-user list order
- createdAt: epoch millis
- updatedAt: epoch millis used for list-metadata reconciliation
- onlineState: `LOCAL`, `ONLINE_OWNER`, `ONLINE_MEMBER`

ItemEntity:
- id: UUID string
- listId: owning list UUID
- description
- quantity: nullable; Shopping only
- completed
- position: explicit persisted item order
- createdAt
- updatedAt
- deletedAt: nullable epoch millis tombstone for online-safe deletion

Room remains the authoritative local/cache copy used by the Android UI. Online-backed lists reconcile against authoritative Supabase snapshots/discovery results when refreshed.

Legacy upgrade:
- Legacy 1.1 SharedPreferences JSON is imported only when the Room database has no lists and genuine `todo_items` / `shopping_items` keys exist.
- A fresh 2.0 install starts with zero lists and must not fabricate legacy To-do/Shopping lists.
- Genuine upgrade import creates ordinary To-do and Shopping ListEntity rows and preserves descriptions, quantities, completion and order.
- Room v4 added `lists.updatedAt`; migration initialises it from `createdAt`.
- Existing local data migrates safely through Room schema upgrades; online state defaults to `LOCAL` and item tombstones default to null.
- Legacy JSON is left untouched during import.
- `LegacySimpleListItem` exists only for import compatibility; new writes must not use the old JSON format.
- Before public 2.0 release, perform a real Google-signed update from installed 1.1 and verify preservation of To-do/Shopping items, quantities, completed states and font scale.

2.0 LIST MODEL / UI
-------------------
- Every list has a user-controlled name independent of its kind.
- Names do not need to be unique; UUID is identity.
- Valid examples: `Bunnings` / SHOPPING, `House jobs` / TODO, `Monday toolbox meeting` / DISCUSSION.
- New-list flow is Type -> Name -> Create.
- Default names: `To-do list`, `Shopping list`, `Discussion points`.
- Default names are fully selected ready to overwrite. Changing type updates/reselects only while the name is blank or still a previous default; custom text is preserved.
- Creating a list now navigates directly into the newly created list using pager `requestScrollToPage`.
- Renaming changes only name; it must not alter UUID, kind, contents, sharing identity or membership.
- Zero lists is valid. Deleting the final list leaves a `No lists` / `+ New list` state.
- Permanent 1.1 tabs are removed in 2.0.
- One current list fills the screen.
- Horizontal swipe moves to the adjacent list. The list strip is not circular; both directions have a natural end.
- Horizontal swipe is the primary nearby-list navigation.
- The current list title is plain identity text and is no longer clickable or decorated with a selector chevron.
- A permanent `+ List` action beside the current heading opens New list directly.
- The top-right hamburger is intentionally small and stable: `Manage lists`, `Sharing`, `About`.
- Individual list shortcuts were deliberately removed from the hamburger because swipe already provides fast adjacent navigation and a growing list set would make the root menu noisy.
- `Manage lists` is the canonical arbitrary-list navigation and administration surface. Tapping a list's main name/details area opens that list; actions alongside it handle Share, Rename and Delete/Leave.
- `Manage lists` reuses the existing full-width list-management view rather than creating a second management UI.
- Local lists show `Share`; online owners no longer show Share; online members use the exact action label `Leave list` rather than Delete.
- Online/shared list identity is marked by a small muted chain/link icon beside the list name. The icon is a separate status element, not part of the stored name.
- Android uses the same 24x24 chain-link path geometry as the browser SVG via `res/drawable/ic_online_list.xml`, rendered at about 15 dp with `onSurfaceVariant`.
- The online icon appears beside the current list heading and beside online lists in Manage lists for both `ONLINE_OWNER` and `ONLINE_MEMBER`; local lists have no icon.
- Visible text `Refresh` was removed. Pull-to-refresh on the current list now performs discovery/reconciliation and reloads Room-backed lists/items.
- Pull refresh remains a deliberate user fallback; Realtime remains the normal change signal.
- Back closes Manage lists before Android can leave the app.

Item ordering:
- New items are inserted at the top by assigning a position below the current minimum.
- The active LazyColumn scrolls to the newly added item so it stays visible under the soft keyboard.
- Display ordering respects persisted `position`, then `createdAt`, while incomplete items are presented before completed items.
- Toggling completion changes completion state, not item position.
- Explicit persisted position remains the basis for future manual item reordering.
- Manual item reordering should work for all list kinds.
- Discussion points may later render derived numbering from item order.
- Manual list ordering is also planned and should use persisted per-user membership/list position.
- Bulk uncheck is implemented as a checkbox in the list column-heading row, aligned directly above the item checkboxes (`checkbox / Qty / Item` for Shopping and `checkbox / Item` for other kinds). It is checked/enabled whenever at least one item is completed and disabled/empty otherwise. Tapping it unchecks all completed items using the normal item-update/sync path. A temporary `Undo` restores only items that have not been changed since the bulk operation, so a newer change from another client is not overwritten.

Editing UX:
- Existing items edit inline.
- Existing item descriptions enter editing with the cursor at the end rather than selecting the whole description.
- Shopping Qty selects its entire existing value on focus so typing replaces it immediately.
- Qty select-all is applied after focus settles so the tap does not overwrite the selection.
- Shopping edit Qty is 48 x 48 dp.
- Edit description is 48 dp high, matching the normal entry geometry.
- Item Cancel logic is centralised and shared by the visible Cancel button and Android Back.
- Default/new-name style editors may still use select-all where overwrite-ready behaviour is appropriate.

Visual/interaction decisions:
- Keep list rows compact without making controls fiddly.
- Use available phone width for item text; avoid unnecessary outer padding.
- Add/Delete remain visually secondary.
- Pinch resizes list/content text, not structural UI such as app title, list controls, headings, Add/Delete text or hint.
- Two-finger pinch must not consume one-finger horizontal paging or vertical scrolling.
- Pinch hint uses actual rendered space and a reserved bottom area.
- Use Manrope throughout all Material typography roles and normal app text.
- Menus/dialogs use the same white surface family as the app.
- Use the JSimpleList logo blue/cyan colour family.
- User-facing informational phrases generally omit trailing full stops.
- Prefer purpose-led wording. Authentication/account controls are presented under `Sharing`; use `Email address`, not ambiguous `Email`.

ONLINE ACCOUNT / OWNERSHIP
--------------------------
- Online identities are persistent Supabase Auth users with stable UUIDs.
- Local-only use remains account-free.
- JSimpleList must provide a transparent controlled `Delete online account` operation before public 2.0 release.
- Local Room lists on that device are not deleted by online-account deletion.
- Owned online/shared lists are destroyed when the owner's online account is deleted.
- Other members consequently lose access to those owned shared lists.
- Account deletion must be a controlled privileged server-side operation; no service-role/admin secret may ship in Android.
- A non-owner member may leave a shared list but may not destroy it.
- An owner may remove individual members while leaving the list alive for remaining members.
- Owner destruction ejects all members.
- Deletion/removal must be represented long enough for offline clients to learn authoritative server state.
- Exact UX for a removed member's already-cached local copy remains to be decided; never silently present a stale cached copy as if it were still a live shared list.

Supabase:
- Custom schema `jsimplelist` exposed for the Data API.
- SQL migrations 001-023 live under `migrations/` and have been manually applied through the Supabase SQL editor as developed.
- Implemented concepts include profiles/users, lists, list_members, invitations, items, tombstones, list metadata timestamps, discovery and private realtime broadcast authorisation.
- Local Room UUIDs are reused as remote UUIDs for online-backed lists/items.
- `list_members.position` stores per-user list order.
- `items.position` stores shared item order within a list.
- Normal list/item reads hide deleted rows.
- Controlled sync snapshot exposes active/deleted/removed/not_found state so offline clients can learn tombstones/removal without weakening normal RLS reads.
- Sensitive membership/list-creation/deletion paths use controlled security-definer RPCs rather than unrestricted direct writes.
- Direct list creation is revoked; use the controlled creation RPC.
- Normal active members may write permitted item/list changes under RLS.
- Supabase URL and publishable key are supplied through local BuildConfig/local.properties.
- Publishable key may ship in the APK.
- Never put a Supabase secret/service-role key or Resend API key in the app or repository.

Important RPC/state contract:
- `create_online_list(...)` creates the list and owner membership while preserving the client UUID.
- `get_list_sync_snapshot(target_list_id uuid)` returns authoritative JSON state including active/deleted/removed/not_found; active state includes list, current membership and items including tombstones.
- `get_my_online_lists()` returns the signed-in user's active online-list memberships with list metadata, role and per-user position. Android uses this for discovery/import of lists not already present in Room.
- `set_my_list_position()` changes the current user's membership/list order without changing another member's order.
- `delete_online_item(target_item_id uuid, target_origin_client_id uuid)` creates the server tombstone and records the transient origin used for realtime self-suppression.
- Browser bulk Delete all uses the controlled online-item bulk-delete path rather than hard deletion.
- `rename_online_list(target_list_id uuid, target_name text, target_origin_client_id uuid)` is owner-controlled, updates list metadata and participates in list realtime signalling.
- `delete_online_list(target_list_id uuid, target_origin_client_id uuid)` is owner-only and retry-safe; it tombstones the list and broadcasts through the list UPDATE trigger.
- `leave_online_list(target_list_id uuid)` is non-owner only and retry-safe; it marks the caller's membership removed. Owners cannot use Leave list.

Realtime contract:
- Per-list private topic: `jsimplelist:list:<list UUID>`.
- Authorised recipients are the list owner or an active member.
- Database item INSERT/UPDATE changes emit a lightweight private `list_changed` Broadcast containing only `list_id` and optional `origin_client_id`.
- List UPDATEs also broadcast `list_changed`, covering rename and server tombstone/deletion.
- Broadcast payloads are notifications only; clients do not trust them as row data. A receiving client loads and reconciles authoritative state.
- Each Android installation has a persistent random client instance UUID.
- Android writes include that UUID as `origin_client_id`; the originating client ignores the matching broadcast.
- The origin is transient server metadata and is cleared after signalling so later/manual server changes are not falsely attributed to an old client.
- Migration 019 fixed PostgreSQL/PostgREST UPSERT double-signalling so an originating edit produces one self-identifiable broadcast rather than a second null-origin broadcast.
- Per-list realtime cannot discover an entirely unknown list UUID. Account/user-level list-set realtime is still needed for immediate create/share/remove discovery; startup/sign-in/pull discovery remains the fallback.

LIST SYNC FOUNDATION
--------------------
The Android online-list contract now supports local-first writes, safe item deletion, list discovery, list metadata reconciliation, owner deletion/member leave, pull-to-refresh and per-list realtime signalling.

Current behaviour:
- Local lists remain local and are never uploaded merely because the user signs in.
- Lists persist `LOCAL`, `ONLINE_OWNER` or `ONLINE_MEMBER` in Room.
- A local list can be explicitly shared from Manage lists.
- Successful sharing persists `ONLINE_OWNER` and removes the Share action for that list.
- `create_online_list` is retry-safe for an existing list owned by the same user.
- Room list/item UUIDs are preserved as Supabase UUIDs.
- `makeListOnline(list, items, originClientId)` pushes the current item set and then loads the authoritative snapshot.
- Add, edit, tick and untick operations write Room first and then automatically push the individual item to Supabase when the list is online.
- Online item deletion uses a local `deletedAt` tombstone plus controlled server tombstone RPC rather than hard-deleting the sync identity.
- Local-only lists continue to write Room only.
- Android discovery calls `get_my_online_lists()` at startup when signed in and after successful sign-in. Remote owner lists absent from Room import as `ONLINE_OWNER`; remote member lists import as `ONLINE_MEMBER`.
- Discovery also reconciles existing list membership position/state and applies newer remote list metadata by `updatedAt`, then refreshes each discovered list snapshot.
- The discovery path was proven on-device by restoring a server-backed list that had previously been deleted only from local Room; its remote name and item completion state matched browser state.
- Pull-to-refresh on the current list runs online-list discovery/reconciliation, reloads Room lists/items and keeps the same list selected when it still exists.
- Reconciliation imports missing remote items, applies remote tombstones, and applies newer remote active rows while avoiding stale resurrection.
- Supabase Realtime subscribes only to the currently displayed online list.
- A remote `list_changed` Broadcast triggers authoritative refresh/reconciliation.
- Broadcasts from the same client instance are ignored where origin metadata is available.
- The full Room copy remains available offline.
- The last active list ID is persisted and restored safely across app restarts.
- Owner Delete list now calls `delete_online_list` first and only removes the local Room list after server success.
- Member `Leave list` calls `leave_online_list` first and only removes the local Room list after server success.
- Local `Delete list` remains Room-only.
- Server-side owner deletion was proven: after deleting an online owner list on Android, it did not respawn after Android restart/discovery.

Important limitations still to implement:
- Failed online writes retain the Room change, but durable retry/reconciliation of those failed writes is not yet implemented.
- Realtime is a change signal, not a replay log; startup/sign-in/pull discovery is currently the missed-signal safety net. A dedicated foreground lifecycle refresh may still be useful later.
- Account-level realtime for list-set changes is not yet implemented, so an unknown newly shared/created list is not discovered instantly while the app remains open.
- Android's separate Rename action is still local-only; server/browser rename exists but Android rename must be wired to `rename_online_list` with updatedAt/origin semantics.
- Manual list ordering is not yet synced.
- Invitations/member management UI is not yet implemented even though `ONLINE_MEMBER` discovery/state now exists.
- Realtime change bursts are not currently debounced/coalesced; household-scale use is acceptable, but this can be improved later if necessary.

BROWSER CLIENT
--------------
- Browser access uses the same Supabase account/list/membership/sync service as Android at `https://jslist.jobsheet.com.au`.
- Browser is another client, not a phone bridge and not a separate backend. It exposes online-backed lists only; local-only lists never leave the phone and therefore never appear in browser.
- A React + TypeScript + Vite client lives under `web/`.
- Browser Supabase configuration uses `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`; real values live only in ignored local/deployment environment configuration.
- Email OTP sign-in works against the existing Supabase Auth account, and the browser session persists normally.
- The signed-in browser currently discovers active online lists through `list_members` plus `lists`, preserving per-user membership order.
- Opening a list calls `get_list_sync_snapshot(target_list_id)` and renders authoritative active items, Shopping quantity, completion state and the same incomplete-before-completed presentation.
- Browser item creation uses true INSERT, not UPSERT, because live testing proved INSERT follows the intended Android realtime trigger path.
- Browser item edit/tick/untick writes carry fresh `updated_at` and `origin_client_id`.
- Browser safe delete uses `delete_online_item`; Delete all uses the controlled bulk tombstone path.
- Browser bulk Uncheck all controls are implemented.
- Browser inline list rename is implemented: click the list name to edit; Enter/blur saves, Escape cancels, blank trimmed input does not save.
- Browser list rename uses the controlled `rename_online_list` RPC and list UPDATE realtime.
- Browser list headings use a small muted chain/link SVG beside the stored list name to indicate online status. Android now uses the same path geometry for visual consistency.
- Browser list-selector UI distinguishes list type and Owner/Shared role.
- Browser list names are not modified to include status glyphs; status remains a separate visual element.
- Each browser installation has a persistent random UUID stored in localStorage. Browser writes use it as `origin_client_id`.
- The browser subscribes to the same private per-list `list_changed` Realtime contract as Android and ignores matching own-origin broadcasts.
- Same-account browser <-> Android item changes have been proven for tick/untick, add, edit and safe delete.
- Public hosting is DigitalOcean App Platform Static Site in SYD1, app `jsimplelist`, component `jsimplelist-web`, source `web/`, branch `main`, autodeploy enabled, build command `npm install && npm run build`, output directory `dist`.
- Production configuration exposes only the public Supabase publishable key, never a secret/service-role key.

Current browser limitations / next work:
- Browser cannot yet create lists. Browser-created lists should be online/shared-to-self from birth; browser does not need a local/unshare concept.
- A remotely deleted selected list can remain visibly stale because `openOnlineList` currently sets `List is no longer available` for an inactive snapshot but does not clear `selectedSnapshot` or reload `onlineLists`. It eventually disappears when list discovery reruns (for example after session refresh), but immediate eviction/reload is required.
- Browser list discovery is not account-level realtime. New/removed memberships or entirely new list UUIDs require discovery to rerun.
- Browser does not remember the last-opened list by design.
- Browser Undo for bulk Uncheck all remains a possible follow-up; Android already has conservative Undo.
