PROJECT
-------
Name: JSimpleList
Package: au.com.jobsheet.jsimplelist
Local project: D:\simplelist
Public repository: https://github.com/jobsheet-aus/JSimpleList
Purpose: Small local-first native Android list app. Version 2.0 generalises the original fixed To-do and Shopping lists into user-named dynamic lists and adds optional online sync/sharing.
Intrinsic list kinds: TODO, SHOPPING and DISCUSSION. Shopping differs by having a Qty field.
Google Play is the intended public distribution channel.

CORE PRODUCT PRINCIPLES
-----------------------
- Keep JSimpleList deliberately small, direct and local-first.
- Local-only use requires no account and must continue to work without internet or backend availability.
- Signing in must never automatically upload existing local lists.
- A local list becomes online only through an explicit user action for that specific list.
- Online/shared lists remain fully cached in Room and usable offline.
- Use one common list model for household and business/work sharing; do not create a separate team hierarchy unless it becomes genuinely useful.
- Preserve local UUIDs as server UUIDs for online-backed lists/items; never create a second identity for the same record.
- List ownership is absolute. The creator remains owner; ownership is not transferred or inherited.
- Back cancels/closes the most local active operation first. Only when nothing transient is active should Back be allowed to leave JSimpleList.
- Existing-value editing behaviour is field-specific: short replacement-style values such as Qty/default names select all, while item descriptions place the cursor at the end so small wording edits do not risk replacing the whole description.

2.0 LOCAL DATA MODEL
--------------------
Room schema version 3 contains `lists` and `items`.

ListEntity:
- id: UUID string
- name: user-controlled
- kind: TODO / SHOPPING / DISCUSSION
- position: explicit persisted list order
- createdAt: epoch millis
- onlineState: `LOCAL`, `ONLINE_OWNER`, future `ONLINE_MEMBER`

ItemEntity:
- id: UUID string
- listId: owning list UUID
- description
- quantity: nullable; Shopping only
- completed
- position: explicit persisted item order
- createdAt
- updatedAt
- deletedAt: nullable epoch millis tombstone for online-safe deletion

Room remains the authoritative local/cache copy used by the Android UI. Online-backed lists reconcile against authoritative Supabase snapshots when refreshed.

Legacy upgrade:
- Legacy 1.1 SharedPreferences JSON is imported only when the Room database has no lists and genuine `todo_items` / `shopping_items` keys exist.
- A fresh 2.0 install starts with zero lists and must not fabricate legacy To-do/Shopping lists.
- Genuine upgrade import creates ordinary To-do and Shopping ListEntity rows and preserves descriptions, quantities, completion and order.
- Existing local data migrates safely through Room schema upgrades; online state defaults to `LOCAL` and item tombstones default to null.
- Legacy JSON is left untouched during import.
- `LegacySimpleListItem` exists only for import compatibility; new writes must not use the old JSON format.
- Before public 2.0 release, perform a real Google-signed update from installed 1.1 and verify preservation of To-do/Shopping items, quantities, completed states and font scale.

2.0 LIST MODEL / UI
-------------------
- Every list has a user-controlled name independent of its kind.
- Names do not need to be unique; UUID is identity.
- Valid examples: `Bunnings` / SHOPPING, `House jobs` / TODO, `Monday toolbox meeting` / DISCUSSION.
- New-list flow is Type -> Name -> Create.
- Default names: `To-do list`, `Shopping list`, `Discussion points`.
- Default names are fully selected ready to overwrite. Changing type updates/reselects only while the name is blank or still a previous default; custom text is preserved.
- Renaming changes only name; it must not alter UUID, kind, contents, sharing identity or membership.
- Zero lists is valid. Deleting the final list leaves a `No lists` / `+ New list` state.
- Permanent 1.1 tabs are removed in 2.0.
- One current list fills the screen.
- Horizontal swipe moves to the adjacent list.
- Tapping the current list title/chevron opens the full-width Lists selector for direct navigation and list management; the previous standalone `Lists` button was removed to reduce header clutter.
- The Lists selector currently provides `+ New list`, Rename and Delete.
- The selector header provides an explicit `Close` action. Tapping blank space also closes it, and tapping a list navigates to it.
- Create/Rename/Delete dialogs close themselves without implicitly closing the underlying Lists view.
- Back closes the Lists selector before Android can leave the app.
- The selector is the intended home for future list reordering, Local/Synced/Shared metadata, unseen markers and owner/member actions.

Item ordering:
- New items are inserted at the top by assigning a position below the current minimum.
- The active LazyColumn scrolls to the newly added item so it stays visible under the soft keyboard.
- Display ordering respects persisted `position`, then `createdAt`, while incomplete items are presented before completed items.
- Toggling completion changes completion state, not item position.
- Explicit persisted position remains the basis for future manual item reordering.
- Manual item reordering should work for all list kinds.
- Discussion points may later render derived numbering from item order.
- Manual list ordering is also planned and should use persisted list position.
- Bulk uncheck is implemented as a checkbox in the list column-heading row, aligned directly above the item checkboxes (`checkbox / Qty / Item` for Shopping and `checkbox / Item` for other kinds). It is checked/enabled whenever at least one item is completed and disabled/empty otherwise. Tapping it unchecks all completed items using the normal item-update/sync path. A temporary `Undo` restores only items that have not been changed since the bulk operation, so a newer change from another client is not overwritten. Real-device testing confirmed the final placement and behaviour.

Editing UX:
- Existing items edit inline.
- Existing item descriptions enter editing with the cursor at the end rather than selecting the whole description. This is intentional because description edits are commonly small changes such as `grapes` -> `purple grapes`.
- Shopping Qty selects its entire existing value on focus so typing replaces it immediately.
- Qty select-all is applied after focus settles so the tap does not overwrite the selection.
- Shopping edit Qty is 48 x 48 dp.
- Edit description is 48 dp high, matching the normal entry geometry.
- Item Cancel logic is centralised and shared by the visible Cancel button and Android Back.
- Default/new-name style editors may still use select-all where overwrite-ready behaviour is appropriate.

Visual/interaction decisions:
- Keep list rows compact without making controls fiddly.
- Use available phone width for item text; avoid unnecessary outer padding.
- Add/Delete remain visually secondary.
- Pinch resizes list/content text, not structural UI such as app title, list controls, headings, Add/Delete text or hint.
- Two-finger pinch must not consume one-finger horizontal paging or vertical scrolling.
- Pinch hint uses actual rendered space and a reserved bottom area.
- Use Manrope throughout all Material typography roles and normal app text.
- Menus/dialogs use the same white surface family as the app.
- Use the JSimpleList logo blue/cyan colour family.
- User-facing informational phrases generally omit trailing full stops.
- Prefer purpose-led wording. Authentication is presented under `List sharing`; use `Email address`, not ambiguous `Email`.

ONLINE ACCOUNT / OWNERSHIP
--------------------------
- Online identities are persistent Supabase Auth users with stable UUIDs.
- Local-only use remains account-free.
- JSimpleList must provide a transparent controlled `Delete online account` operation before public 2.0 release.
- Local Room lists on that device are not deleted by online-account deletion.
- Owned online/shared lists are destroyed when the owner's online account is deleted.
- Other members consequently lose access to those owned shared lists.
- Account deletion must be a controlled privileged server-side operation; no service-role/admin secret may ship in Android.
- A non-owner member may leave a shared list but may not destroy it.
- An owner may remove individual members while leaving the list alive for remaining members.
- Owner destruction ejects all members.
- Deletion/removal must be represented long enough for offline clients to learn authoritative server state.
- Exact UX for a removed member's already-cached local copy remains to be decided; never silently present a stale cached copy as if it were still a live shared list.

SUPABASE BACKEND FOUNDATION
---------------------------
Committed milestones include:
    ee9e561 Add Supabase backend foundation
    14f7277 Add Supabase Android client
    e9a0f09 Update JSimpleList Supabase context
    76fdf45 Add safe online item tombstones
    7c98a9c Add realtime list refresh and sync signalling

Supabase:
- Custom schema `jsimplelist` exposed for the Data API.
- SQL migrations 001-019 live under `migrations/`.
- Implemented concepts include profiles/users, lists, list_members, invitations, items, tombstones and private realtime broadcast authorisation.
- Local Room UUIDs are reused as remote UUIDs for online-backed lists/items.
- `list_members.position` stores per-user list order.
- `items.position` stores shared item order within a list.
- Normal list/item reads hide deleted rows.
- Controlled sync snapshot exposes active/deleted/removed/not_found state so offline clients can learn tombstones/removal without weakening normal RLS reads.
- Sensitive membership/list-creation/deletion paths use controlled security-definer RPCs rather than unrestricted direct writes.
- Direct list creation is revoked; use the controlled creation RPC.
- Normal active members may write permitted item/list changes under RLS.
- Supabase URL and publishable key are supplied through local BuildConfig/local.properties.
- Publishable key may ship in the APK.
- Never put a Supabase secret/service-role key or Resend API key in the app or repository.

Important RPC/state contract:
- `create_online_list(target_list_id uuid, target_name text, target_kind text, target_position integer, target_created_at timestamptz, target_updated_at timestamptz)` creates the list and owner membership.
- `get_list_sync_snapshot(target_list_id uuid)` returns authoritative JSON state including active/deleted/removed/not_found; active state includes list, current membership and items including tombstones.
- `set_my_list_position()` changes the current user's membership/list order without changing another member's order.
- `delete_online_item(target_item_id uuid, target_origin_client_id uuid)` creates the server tombstone and records the transient origin used for realtime self-suppression.

Realtime contract:
- Private topic: `jsimplelist:list:<list UUID>`.
- Authorised recipients are the list owner or an active member.
- Database item INSERT/UPDATE changes emit a lightweight private `list_changed` Broadcast containing only `list_id` and optional `origin_client_id`.
- Broadcast payloads are notifications only; clients do not trust them as row data. A receiving client loads and reconciles the authoritative snapshot.
- Each Android installation has a persistent random client instance UUID.
- Android writes include that UUID as `origin_client_id`; the originating client ignores the matching broadcast.
- The origin is transient server metadata and is cleared after signalling so later/manual server changes are not falsely attributed to an old client.
- Migration 019 fixes PostgreSQL/PostgREST UPSERT double-signalling so an originating edit produces one self-identifiable broadcast rather than a second null-origin broadcast.

LIST SYNC FOUNDATION
--------------------
The Android online-list contract now supports local-first writes, safe deletion, manual authoritative refresh and realtime refresh signalling.

Current behaviour:
- Local lists remain local and are never uploaded merely because the user signs in.
- Lists persist an `onlineState` value in Room.
- Current states are `LOCAL`, `ONLINE_OWNER` and future `ONLINE_MEMBER`.
- A local list can be explicitly shared from the Lists management surface.
- Successful sharing persists `ONLINE_OWNER` and removes the Share action for that list.
- `create_online_list` is retry-safe for an existing list owned by the same user.
- Room list/item UUIDs are preserved as Supabase UUIDs.
- `makeListOnline(list, items, originClientId)` upserts the current item set and then loads the authoritative snapshot.
- Add, edit, tick and untick operations write Room first and then automatically upsert the individual item to Supabase when the list is online.
- Online deletion uses a local `deletedAt` tombstone plus controlled server tombstone RPC rather than hard-deleting the sync identity.
- Local-only lists continue to write Room only.
- Manual `Refresh` is available on the current online list. It loads `get_list_sync_snapshot`, merges remote items/tombstones into Room by UUID/timestamp, reloads the visible list and reports success/failure.
- Reconciliation imports missing remote items, applies remote tombstones, and applies newer remote active rows while avoiding stale resurrection.
- Remote manual/server changes must advance `updated_at` to win timestamp reconciliation.
- Supabase Realtime subscribes only to the currently displayed online list.
- A remote `list_changed` Broadcast triggers the same snapshot reconciler and updates the visible Room-backed list.
- Broadcasts from the same Android client instance are ignored, preventing needless self-refresh.
- Realtime server -> Android refresh and Android own-origin suppression have both been proven on a physical device.
- The full Room copy remains available offline.
- The last active list ID is persisted and restored safely across app restarts.

Important limitations still to implement:
- Failed online writes retain the Room change, but durable retry/reconciliation of those failed writes is not yet implemented.
- Realtime is a change signal, not a replay log; a client disconnected during a change can miss the signal.
- Add a sensible app-foreground snapshot refresh as a safety net without aggressive polling.
- List-level changes such as rename and ordering are not yet synchronised.
- Shared-member import and `ONLINE_MEMBER` behaviour are not yet implemented.
- Invitations/member controls and owner/member leave/remove/destroy UX remain to implement.
- Realtime change bursts are not currently debounced/coalesced; household-scale use is acceptable, but this can be improved later if necessary.

BROWSER CLIENT
--------------
- Browser access uses the same Supabase account/list/membership/sync service as Android. Preferred hostname remains `jslist.jobsheet.com.au`.
- Browser is another client, not a phone bridge and not a separate backend. It exposes online-backed lists only; local-only lists never leave the phone and therefore never appear in browser.
- A React + TypeScript + Vite client lives under `web/`. Foundation was committed in `bc6aa4a`; everyday item CRUD was completed in `91a997c`.
- Browser Supabase configuration uses `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`; real values live only in ignored `web/.env.local`. `.env.example` documents both variable names.
- Email OTP sign-in works against the existing Supabase Auth account, and the browser session persists normally.
- The signed-in browser discovers active online lists through `list_members` plus `lists`, preserving per-user membership order.
- Opening a list calls `get_list_sync_snapshot(target_list_id)` and renders authoritative active items, Shopping quantity, completion state and the same incomplete-before-completed presentation.
- Browser checkbox tick/untick writes the full current item row with a fresh `updated_at` and `origin_client_id`, then reloads the authoritative snapshot.
- Browser item creation uses a true INSERT with a new UUID, the same position rule as Android, and one creation/update timestamp. Using UPSERT for brand-new browser rows did not produce the required Android realtime behaviour; INSERT is the proven creation path.
- Browser item editing supports description and Shopping quantity. Clicking description focuses description with the cursor at the end; clicking Qty focuses Qty and selects the whole value. Save commits, while Cancel, Escape and clicking outside the edit row abandon the edit.
- Browser safe delete calls `delete_online_item(target_item_id, target_origin_client_id)` so deletion is represented by the existing server tombstone contract rather than a hard delete.
- Browser refreshes keep the existing list rendered instead of temporarily replacing it with a loading state, avoiding visible list disappearance after add/edit/delete/tick operations.
- Browser Delete is intentionally a small blue secondary action to mirror Android's visual grammar rather than using a harsh destructive red.
- Each browser installation has a persistent random UUID stored in localStorage. Browser writes use it as `origin_client_id`.
- The browser subscribes to the same private `jsimplelist:list:<list UUID>` / `list_changed` Realtime contract as Android. It ignores matching own-origin broadcasts and reloads the authoritative snapshot for genuine remote changes.
- Same-account browser -> Android and Android -> browser realtime changes have been proven for tick/untick, add, edit and safe delete. Manual Refresh remains available as a fallback and snapshot reconciliation recovers previously missed server changes.
- The browser client is publicly deployed at `https://jslist.jobsheet.com.au`.
- Hosting is DigitalOcean App Platform as a Static Site in SYD1, app `jsimplelist`, component `jsimplelist-web`, source `web/`, branch `main`, autodeploy enabled, build command `npm install && npm run build`, output directory `dist`.
- Production configuration uses DigitalOcean environment variables `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`. Only the public Supabase publishable key is used; no secret/service-role key is exposed.
- Custom DNS uses `jslist.jobsheet.com.au` CNAME to the DigitalOcean starter hostname. HTTPS is working.
- Public live testing confirmed the deployed browser can sign in and operate correctly against the existing online-list service.
