PROJECT
-------
Name: JSimpleList
Package: au.com.jobsheet.jsimplelist
Local project: D:\simplelist
Public repository: https://github.com/jobsheet-aus/JSimpleList
Purpose: Small local-first native Android list app. Version 2.0 generalises the original fixed To-do and Shopping lists into user-named dynamic lists and adds optional online sync/sharing.
Intrinsic list kinds: TODO, SHOPPING and DISCUSSION. Shopping differs by having a Qty field.
Google Play is the intended public distribution channel.

CORE PRODUCT PRINCIPLES
-----------------------
- Keep JSimpleList deliberately small, direct and local-first.
- Local-only use requires no account and must continue to work without internet or backend availability.
- Signing in must never automatically upload existing local lists.
- A local list becomes online only through an explicit user action for that specific list.
- Online/shared lists remain fully cached in Room and usable offline.
- Use one common list model for household and business/work sharing; do not create a separate team hierarchy unless it becomes genuinely useful.
- Preserve local UUIDs as server UUIDs for online-backed lists/items; never create a second identity for the same record.
- List ownership is absolute. The creator remains owner; ownership is not transferred or inherited.
- Back cancels/closes the most local active operation first. Only when nothing transient is active should Back be allowed to leave JSimpleList.
- Existing-value editing behaviour is field-specific: short replacement-style values such as Qty/default names select all, while item descriptions place the cursor at the end so small wording edits do not risk replacing the whole description.

2.0 LOCAL DATA MODEL
--------------------
Room schema version 6 contains `lists`, `items` and `list_accounts`.

ListEntity:
- id: UUID string
- name: user-controlled
- kind: TODO / SHOPPING / DISCUSSION
- position: explicit persisted list order/cache position
- createdAt: epoch millis
- updatedAt: epoch millis used for list-metadata reconciliation
- onlineState: legacy/current-render convenience value `LOCAL`, `ONLINE_OWNER` or `ONLINE_MEMBER`; account-specific authority now lives in `list_accounts`

ItemEntity:
- id: UUID string
- listId: owning list UUID
- description
- quantity: nullable; Shopping only
- completed
- position: explicit persisted item order
- createdAt
- updatedAt
- deletedAt: nullable epoch millis tombstone for online-safe deletion
- createdByUserId: nullable authenticated creator UUID for shared-item attribution
- updatedByUserId: nullable authenticated UUID of the most recent editor

ListAccountEntity / `list_accounts`:
- composite primary key `(listId, accountId)`
- listId references `lists(id)` with ON DELETE CASCADE
- accountId is the authenticated Supabase user UUID
- onlineState is the role/state for that account on that list, currently `ONLINE_OWNER` or `ONLINE_MEMBER`
- the same cached list may therefore be owner for one account and member for another on the same device
- a genuinely device-local list has no `list_accounts` relationship rows

Visibility contract:
- local lists belong to the device and remain visible whether signed in or signed out
- shared/online lists belong to authenticated user relationships, not to the device as a whole
- signed out: show only genuine local lists
- signed in as account A: show local lists plus online lists related to account A
- account A's online lists must not remain visible merely because account B later signs in on the same device
- `loadVisibleLists(accountId)` projects the active account's relationship `onlineState` into the returned `ListEntity`
- legacy online rows with no `list_accounts` relationship are deliberately hidden until authoritative Supabase discovery associates them with the signed-in account

Room remains the local/cache copy used by the Android UI. Online-backed lists reconcile against authoritative Supabase discovery/snapshot results.

Legacy upgrade:
- Legacy 1.1 SharedPreferences JSON is imported only when the Room database has no lists and genuine `todo_items` / `shopping_items` keys exist.
- A fresh 2.0 install starts with zero lists and must not fabricate legacy To-do/Shopping lists.
- Genuine upgrade import creates ordinary To-do and Shopping ListEntity rows and preserves descriptions, quantities, completion and order.
- Room v4 added `lists.updatedAt`; migration initialises it from `createdAt`.
- Room v5 adds `list_accounts`; migration 4->5 creates the relationship table and indexes without guessing account ownership for pre-existing online cache rows.
- Room v6 adds nullable `createdByUserId` and `updatedByUserId` item attribution fields; migration 5->6 preserves all existing item data and leaves historic attribution unknown/null.
- Existing local data migrates safely through Room schema upgrades; item tombstones default to null.
- Legacy JSON is left untouched during import.
- `LegacySimpleListItem` exists only for import compatibility; new writes must not use the old JSON format.
- Before public 2.0 release, perform a real Google-signed update from installed 1.1 and verify preservation of To-do/Shopping items, quantities, completed states and font scale.

2.0 LIST MODEL / UI
-------------------
- Every list has a user-controlled name independent of its kind.
- Names do not need to be unique; UUID is identity.
- Valid examples: `Bunnings` / SHOPPING, `House jobs` / TODO, `Monday toolbox meeting` / DISCUSSION.
- New-list flow is Type -> Name -> Create.
- Default names: `To-do list`, `Shopping list`, `Discussion points`.
- Default names are fully selected ready to overwrite. Changing type updates/reselects only while the name is blank or still a previous default; custom text is preserved.
- Creating a list navigates directly into the newly created list using pager `requestScrollToPage`.
- Renaming changes only name; it must not alter UUID, kind, contents, sharing identity or membership.
- Zero lists is valid. Deleting the final list leaves a `No lists` state with a New list path.
- Permanent 1.1 tabs are removed in 2.0.
- One current list fills the screen; horizontal swipe moves to adjacent lists with natural ends.
- Manage lists remains the canonical arbitrary-list navigator/admin surface.
- Planned fast deletion shortcut: long-press the current list title to open the existing delete confirmation; Manage lists -> Delete remains the discoverable path.
- Planned creation/share shortcut: after creating a list, offer `Share this list?`; choosing Share should automatically perform any necessary make-online transition and continue directly into invitation flow.
- Online/shared list identity is marked by the muted chain/link icon; local lists are unmarked.
- Pull-to-refresh performs discovery/reconciliation; visible `Refresh` text is removed.
- Back closes Manage lists before Android can leave the app.

Current account/menu/sharing UX:
- JSimpleList deliberately supports one authenticated account at a time per device for clarity.
- Hamburger contains `New list`, `Manage lists`, `Sharing`, dynamic `Sign in`/`Sign out`, signed-in `Delete account`, and `About`.
- When signed in, the Sign out menu item also shows the authenticated email address in smaller text.
- `Sign in` opens the existing sharing/auth dialog.
- `Sign out` uses a confirmation dialog: `Shared lists will be unavailable on this device until you sign in again. Local lists will remain available.`
- Sign-out reloads `loadVisibleLists(null)`, so shared lists disappear while genuine device-local lists remain.
- Sharing is non-destructive profile/account information. It shows `List sharing is enabled`, `Signed in as` followed by the signed-in email, and a large tappable display name for editing. The older `Signed in as :` punctuation was removed.
- The older `Disable sharing` action has been removed. Account deletion is a separate explicit hamburger action.
- The prominent current-list action is now `Share list`; the former prominent `+ List` action has moved into the hamburger as `New list`.
- `Share list` distinguishes two intentions without exposing the term self-share:
  1. `Use this list on my other devices` / `Make available online` for the current authenticated account.
  2. `Invite someone` by email for another account.
- For an online list, the Share dialog explains that it is available wherever the signed-in account is used and provides the invitation email field.
- Established-user invitation delivery is now implemented and proven on real devices: active Android recipients are classified server-side, receive immediate push without an immediate sign-in email, notification taps route to the relevant invitation/list, and accept/decline retain the authoritative invitation RPC flow. Genuinely new/green-recipient onboarding is the next phase and is not yet complete.

Item ordering:
- New items are inserted at the top by assigning a position below the current minimum.
- The active LazyColumn scrolls to the newly added item so it stays visible under the soft keyboard.
- Display ordering respects persisted `position`, then `createdAt`, while incomplete items are presented before completed items.
- Room v6 adds nullable `createdByUserId` and `updatedByUserId` item attribution fields; migration 5->6 preserves all existing item data and leaves historic attribution unknown/null.
- Toggling completion changes completion state, not item position.
- Explicit persisted position remains the basis for future manual item reordering.
- Manual item reordering should work for all list kinds.
- Discussion points may later render derived numbering from item order.
- Manual list ordering is also planned and should use persisted per-user membership/list position.
- Bulk uncheck is implemented as a checkbox in the list column-heading row, aligned directly above the item checkboxes. Tapping it unchecks all completed items using the normal item-update/sync path; temporary Undo restores only items not changed since the bulk operation.

Editing UX:
- Existing items edit inline.
- Existing item descriptions enter editing with the cursor at the end rather than selecting the whole description.
- Shopping Qty selects its entire existing value on focus so typing replaces it immediately.
- Shopping edit Qty is 48 x 48 dp; edit description is 48 dp high.
- Item Cancel logic is centralised and shared by visible Cancel and Android Back.

Visual/interaction decisions:
- Keep list rows compact without making controls fiddly.
- Use available phone width for item text; avoid unnecessary outer padding.
- Add/Delete remain visually secondary.
- Pinch resizes list/content text, not structural UI.
- Use Manrope throughout all Material typography roles and normal app text.
- Menus/dialogs use the same white surface family as the app.
- Use the JSimpleList logo blue/cyan colour family.
- User-facing informational phrases generally omit trailing full stops.
- Use `Email address`, not ambiguous `Email`.

ONLINE ACCOUNT / OWNERSHIP
--------------------------
- Online identities are persistent Supabase Auth users with stable UUIDs; local-only use remains account-free.
- Shared/online list relationships belong to authenticated users, not to the device globally. Local lists belong to the device.
- Multiple different accounts may use the same Android device sequentially; only the current account's shared lists should be visible, while device-local lists remain visible to either account.
- The same server list may legitimately have multiple `list_accounts` rows on one device, e.g. Account A owner and Account B member.
- `Delete account` is implemented as a separate destructive hamburger action and uses the privileged hosted deletion backend.
- Android account-deletion cleanup is account-scoped: it removes the deleted account's `list_accounts` relationships, removes cached lists that account owned, keeps genuine device-local lists, and does not convert unrelated online cache rows into local lists.
- Disposable-account end-to-end testing succeeded: the Auth user/profile were removed, owned online list data was removed as expected, Android returned to signed-out/local-only state, and no unexplained orphan online data was found.
- Owned online/shared lists are destroyed when the owner's online account is deleted; other members consequently lose access.
- Non-owner account deletion removes membership but deliberately preserves items that user contributed to another owner's shared list because items belong to the list, not to the contributor identity.
- A non-owner member may leave a shared list but may not destroy it; an owner may remove members or destroy the list.
- Account deletion remains a controlled privileged server-side operation; no service-role/admin secret may ship in Android/browser.
- Google Play release work still requires the external/web account-deletion resource/page in addition to the in-app path.
- Dormant empty-account cleanup is deliberately deferred; do not auto-purge accounts merely because they currently own no online lists.

LIST SYNC FOUNDATION
--------------------
The Android online-list contract supports local-first writes, safe item deletion, list discovery, list metadata reconciliation, owner deletion/member leave, pull-to-refresh, per-list realtime signalling and account-scoped cached-list visibility.

Current behaviour:
- Local lists remain local and are never uploaded merely because the user signs in.
- `list_accounts` is now the account-specific authority for whether a cached online list belongs to the currently authenticated user and whether that user is owner/member.
- `discoverOnlineLists()` reads the current Supabase user ID, calls `get_my_online_lists()`, then after successful discovery clears that account's old `list_accounts` relationships and rebuilds them exactly from authoritative results.
- Relationship rebuilding occurs before list snapshot refreshes so a refresh failure does not leave only a partial set of account/list relationships restored.
- `loadVisibleLists(accountId)` returns device-local lists plus only that account's online lists, projecting the account-specific online role into returned `ListEntity.onlineState`.
- Signed-out visibility uses `loadVisibleLists(null)` and therefore shows only device-local lists.
- A local list made online records an `ONLINE_OWNER` `list_accounts` row for the current authenticated account.
- Remote owner/member lists absent from Room import into cache; existing cached list metadata reconciles by `updatedAt`; each discovered list then refreshes authoritative snapshot/items.
- Pull-to-refresh runs discovery/reconciliation; per-list realtime continues to trigger authoritative refresh.
- Add/edit/tick/untick write Room first then push when current rendered list is online; online item deletion uses local/server tombstones.
- Owner Delete list remains server-first; member Leave list remains server-first; local Delete remains Room-only.
- Full Room cache remains available offline, but account visibility rules prevent one account from seeing another account's shared-list cache.
- Last active list ID is persisted/restored safely when still visible.

SHARING / INVITATION DIRECTION
------------------------------
- Invitation rows and the controlled acceptance RPC remain the membership model; URLs/push payloads never directly write membership.
- GREEN onboarding now intentionally treats the emailed high-entropy opaque handoff as a short-lived invitation capability. Passive page inspection grants nothing. Explicit `Join list` may redeem that capability to bootstrap the invited Supabase identity server-side and then invoke `accept_list_invitation()`. Forwarding the invitation link therefore forwards that capability; this is an accepted UX/security trade-off to avoid asking every legitimate recipient to prove the same mailbox twice.
- The GREEN browser journey is deployed and proven: purpose-specific email -> opaque handoff page -> deliberate Join -> session -> authoritative acceptance -> shared list visible.
- Recipient pending invitations for established users remain loaded through `get_my_pending_invitations()`; the RPC excludes deleted lists and returns inviter display name, list name and list kind.
- Android invitation dialogs still offer explicit Decline/Accept for the established-user push/pending-invitation lane.
- Accept remains authoritative through `accept_list_invitation()` and Android reuses `discoverOnlineLists()` for import as `ONLINE_MEMBER`.
- Decline is authoritative through `decline_list_invitation()` and notifies through the durable push machinery.
- Reinviting the same normalised email to the same list supersedes prior invitation lifecycle/history. Already-active members are rejected rather than reinvited.
- Outstanding invitations are cancelled when their list is deleted.
- User-visible sharing notifications have one Android path only: FCM -> system notification tray. The former automatic in-app `Sharing update` fallback remains removed.
- Pending invitation dialogs are actionable application state, not a notification fallback.

- Browser item creation uses true INSERT, not UPSERT, because live testing proved INSERT follows the intended Android realtime trigger path.
- Browser item edit/tick/untick writes carry fresh `updated_at` and `origin_client_id`.
- Browser safe delete uses `delete_online_item`; Delete all uses the controlled bulk tombstone path.
- Browser bulk Uncheck all controls are implemented.
- Browser inline list rename is implemented: click the list name to edit; Enter/blur saves, Escape cancels, blank trimmed input does not save.
- Browser list rename uses the controlled `rename_online_list` RPC and list UPDATE realtime.
- Browser list headings use a small muted chain/link SVG beside the stored list name to indicate online status. Android now uses the same path geometry for visual consistency.
- Browser list-selector UI distinguishes list type and Owner/Shared role.
- Browser list names are not modified to include status glyphs; status remains a separate visual element.
- Each browser installation has a persistent random UUID stored in localStorage. Browser writes use it as `origin_client_id`.
- The browser subscribes to the same private per-list `list_changed` Realtime contract as Android and ignores matching own-origin broadcasts.
- Same-account browser <-> Android item changes have been proven for tick/untick, add, edit and safe delete.
- Public hosting is DigitalOcean App Platform Static Site in SYD1, app `jsimplelist`, component `jsimplelist-web`, source `web/`, branch `main`, autodeploy enabled, build command `npm install && npm run build`, output directory `dist`.
- Production configuration exposes only the public Supabase publishable key, never a secret/service-role key.

Current browser limitations / next work:
- Browser cannot yet create lists. Browser-created lists should be online/shared-to-self from birth; browser does not need a local/unshare concept.
- A remotely deleted selected list can remain visibly stale because `openOnlineList` currently sets `List is no longer available` for an inactive snapshot but does not clear `selectedSnapshot` or reload `onlineLists`. It eventually disappears when list discovery reruns (for example after session refresh), but immediate eviction/reload is required.
