Name: JSimpleList

DESIGN / BEHAVIOUR DECISIONS
----------------------------
- Keep the app deliberately small and local-first.
- To-do item fields: description + completed.
- Shopping item fields: Qty + description + completed.
- Discussion item fields: description + completed.
- Internal list kind is DISCUSSION; user-facing terminology is "Discussion points".
- Discussion lists are intended for meetings/agendas and are architecturally the same basic item model as To-do.
- Shopping Qty defaults to 1.
- Completed items remain visible so they can be unticked.
- Completed Shopping Qty and description should both show strike-through.
- Pinch resizes content text, not structural UI such as the app title, tabs, Qty / Item headings, Add/Delete text or hint.
- Pinch must work regardless of pinch direction; diagonal pinch is normal.
- Do not use whole-screen transformable handling now that horizontal paging exists.
- Two-finger pinch handling must leave one-finger horizontal pager gestures and vertical list scrolling available.
- Horizontal swiping remains the fast sequential way to move to the previous/next list.
- Dynamic-list navigation should not depend on permanent fixed tabs. A dedicated list selector will provide direct access to any list.
- The current list header/selector should show the user-controlled list name and may show compact metadata such as type, incomplete-item count and local/synced/shared state.
- Future shared-list headings should also be able to show a small red unseen-activity marker/star beside the count.
- Pinch hint visibility is based on actual rendered space, with a fixed reserved hint area; it disappears only when list content approaches the bottom hint area.
- Existing items are edited inline.
- Item order within every list kind should be user-editable; do not assume creation/alphabetical order is always what the user wants.
- Persist an explicit item position/order value so To-do, Shopping and Discussion lists can all be manually reordered.
- Discussion points may be presented as a numbered list, with numbering derived from the current item order.
- Keep list rows compact without making controls fiddly.
- Be greedy with horizontal occupancy on phone screens: avoid unnecessary outer padding and use available width for item text.
- Keep Add and Delete visually secondary to list content.
- Use Manrope throughout the app.
- Use the JSimpleList logo blue/cyan colour family throughout.

- Visible/public name is JSimpleList.
- Repository is public on GitHub under jobsheet-aus/JSimpleList.
- Google Play is the intended public distribution channel; direct APK distribution from jobsheet.com.au is not currently planned.
- Do not expose an easy direct support-email channel in the app.

Implemented architecture:
- Added Room 3.0.1 / androidx.room3 database foundation using AndroidSQLiteDriver.
- Room schema version 1 contains `lists` and `items`.
- `lists`: UUID id, user-controlled name, kind, position, createdAt.
- `items`: UUID id, listId FK with cascade delete, description, nullable quantity, completed, position, createdAt, updatedAt.
- Item ordering query keeps incomplete items above completed items while respecting manual position within each group.
- Legacy 1.1 SharedPreferences JSON is imported into Room only when the Room database has no lists.
- Legacy importer creates default `To-do` and `Shopping` ListEntity records and preserves old descriptions, quantities, completed state and list order; old timestamp IDs are retained as createdAt/updatedAt while new Room item IDs are UUIDs.
- Legacy JSON remains untouched during import.
- `SimpleListItem` was renamed to `LegacySimpleListItem`; legacy save/write code was removed so future UI code cannot accidentally continue writing the old JSON format.
- `ListKind` now lives independently in `ListKind.kt` and contains TODO, SHOPPING and DISCUSSION.
- MainActivity now reads and writes `ItemEntity` through Room; add/edit/toggle/delete operations are item-level DAO operations. Room is authoritative for current 2.0 list data.
- MainActivity no longer has separate `todoList`, `shoppingList`, `todoItems` or `shoppingItems` state. It loads an ordered dynamic `ListEntity` collection and an item collection keyed by list UUID.
- Permanent tabs have been removed from the 2.0 dynamic UI.
- One current list fills the main screen; horizontal swipe moves to adjacent lists.
- A dedicated `Lists` control opens a full-width vertical selector for direct navigation.
- The selector is also the current list-management surface: `+ New list`, Rename and Delete.
- Lists can now be created with a user-controlled name and intrinsic type, renamed without changing identity/type/items, and deleted locally.
- Zero lists is a valid state. Deleting the final list shows a `No lists` / `+ New list` empty state rather than recreating To-do/Shopping.
- The rename dialog focuses the name field and selects the full existing name so typing replaces it immediately.
- Basic dynamic-list navigation and management have been tested successfully on the real Android phone.

2.0 dynamic-list model decisions:
- Every list has a user-controlled name. Name and kind are independent concepts.
- List names do not need to be unique because UUIDs are the real identity.
- Example valid combinations: `Bunnings` / SHOPPING, `House jobs` / TODO, `Monday toolbox meeting` / DISCUSSION.
- Creating a list should ask for at least Name and Type. User-facing type labels are To-do, Shopping and Discussion points.
- Renaming a list changes only `ListEntity.name`; it must not change UUID, type, contents, sharing identity or membership.
- Every list and every item carries an explicit position/order field so manual reordering does not require a future schema migration.

2.0 navigation/UI direction:
- Permanent fixed tabs are a 1.1-era navigation model and should not be the long-term dynamic-list UI.
- One selected/current list should occupy the main screen.
- Horizontal left/right swipe remains the fast way to move to the adjacent list in list order.
- Add a dedicated `Lists` selector/control for direct navigation. It should open a full-width vertical list of all lists so many lists and long user-assigned names remain practical.
- The selector is also a natural future home for list reordering and unseen-activity indicators.
- The current-list header should give the list name highest prominence. Compact secondary metadata may include list type, incomplete item count and Local/Synced/Shared state. Member identities/initials can be shown when useful without overwhelming the header.
- Basic list management now lives in the `Lists` selector rather than cluttering the normal list-working screen. Each selector row exposes Rename and Delete; the normal current-list header shows only `Lists`.
- As sharing adds more owner/member actions later, the selector remains the natural management surface and may use a compact per-list menu if the action set becomes too large.
- A more elaborate horizontal wheel/carousel selector is a possible later visual navigation mode. Do not make 2.0 depend on it. The underlying navigation contract should remain simply select-list-by-ID / previous / next so a different selector can be substituted later.

List deletion / ownership semantics:
- Local list: the user can delete it.
- Owned shared list: owner can manage members, eject individual members, rename it and destroy the whole list.
- Shared list owned by someone else: member can leave, but cannot destroy the shared list.
- Owner removing a member must revoke that member's server access while leaving the list alive for remaining members.
- Owner destroying a list ejects all members. Deletion must be represented long enough for offline clients to learn that the authoritative shared list was destroyed.
- Exact UX for what happens to a removed member's already-cached local copy is still to be decided; do not silently treat a stale cached copy as if it were still a live shared list.

FUTURE SHARED LIST DESIGN
-------------------------
This is a wishlist/future feature and is not implemented yet.

Core decision:
- A shared list should be a list in its own right, not a special shared-items section inside an otherwise private Shopping list.
- Household and business/work examples should use the same underlying model.
- Example household list: "Home Shopping" shared by Josh and Kate.
- Example work list: a fittings/materials list shared by multiple plumbers.

Expected behaviour:
- Local To-do and Shopping must continue to work without login or internet.
- Sharing should be optional and should not force registration on ordinary users.
- Shared lists should remain locally cached/offline-capable and synchronize when connectivity returns.
- Shared-list membership belongs directly to each list initially; do not build a global team/group hierarchy unless it becomes genuinely useful.
- A shared list has an owner and may have one or more members.
- The owner may remove/eject individual members while the list continues for the remaining members.
- A non-owner member may leave a shared list but may not destroy it.
- The owner may destroy the list; this terminates membership for everyone.
- Shared-list destruction must propagate reliably to clients that may have been offline, so server-side deletion/tombstone semantics are required rather than relying on an immediate hard delete that an offline client could miss.
- Member removal is a membership event, separate from destruction of the list itself. Membership data should leave room for role/state and removal time rather than being only a timeless list of user IDs.
- When another member adds or changes an item, the user's list header/selector should show a small red unseen-activity star/marker beside the item count.
- A user's own changes do not create an unseen marker for that user.
- The unseen marker should clear when that user actually views the updated list/page.
- The per-user state should be modelled as something like last_seen_at rather than a single global has_notification flag.
- Initially use the in-app unseen marker rather than Android push notifications.
- Android push notifications may be considered later if they prove worthwhile.
- Shared lists should include a manual refresh/reload action for user confidence and recovery.
- Manual refresh must genuinely query server state and reconcile the local copy.
- On successful manual refresh show a short transient message such as "List refreshed".
- On failure show a concise failure message and retain the local cached list.
- Realtime synchronization should normally happen silently; manual refresh is a user-controlled sanity check.

Possible server/backend direction:
- Supabase/PostgreSQL is the leading candidate because it provides authentication, relational membership, Row Level Security and realtime capabilities without requiring a custom Flask service.
- No final backend choice has been committed yet.
- Authentication remains optional for local-only use. For online use, the preferred initial login is an emailed six-digit one-time code with a persistent session; password support can remain optional/later.
- Likely server data concepts: users, lists, list_members, items, plus enough deletion/revision state for reliable offline reconciliation.
- Server-side authorization must ensure only current members of a list can read/change that list and only the owner can perform owner-only membership/destruction operations.
- Room is now implemented as the 2.0 local database foundation and is authoritative for list/item data in the current development branch; SharedPreferences JSON is legacy-import-only.

FUTURE ONLINE / SHARING ARCHITECTURE - 21 AUG 2026
---------------------------------------------------
Core product principle:
- JSimpleList remains local-first.
- Local-only use remains the default and must continue to work without account creation, login, sync or server dependency.
- Online features are optional and should be explicitly enabled only by users who want sync, sharing or browser access.
- Do not automatically upload existing local lists merely because a user signs in or enables online features.
- Individual lists should have independent state rather than forcing the whole app into an online mode.

Expected online relationship states (derive these from online/server relationship rather than encoding them as a rigid intrinsic list-kind enum):
- Local: exists only on the device.
- Synced: user's own online-backed list, available on their devices and in a browser.
- Shared: online-backed list with one or more other members.
- The phone keeps a complete locally usable copy of online lists so normal use remains available offline.
- A list becoming local again should not require a data conversion; the local copy already exists. Ending online access simply removes/disconnects the server relationship as appropriate.
- Shared-list ownership/member semantics must prevent one user from silently destroying a list other members still rely on.

Server authority and sync:
- For synced/shared lists, the server should retain the current authoritative list state while online functionality is active.
- Do not delete list items from the server merely because all current clients have received them; that would make reliable later edits, browser access, new-device sync and membership changes unnecessarily difficult.
- Synchronisation/event history may be pruned after all relevant clients have acknowledged newer state; only current state needs durable retention for this simple product.
- Realtime/background traffic should be conservative. Avoid aggressive polling.
- Prefer sync on meaningful events such as app foreground, local edits, manual refresh and lightweight realtime notification while appropriate.
- If the backend is unavailable or quotas are exhausted, cached/local lists must remain usable and no local data should be lost.

Browser access:
- Browser access should be designed together with sharing because both depend on the same account, list, membership and sync model.
- Preferred hostname is `jslist.jobsheet.com.au` so the JSimpleList/JS identity remains visible.
- The browser frontend is another client of the same online-list service, not a phone bridge and not a separate backend.
- A small web client should expose online-backed lists only.
- Browser scope can remain deliberately minimal: choose list, add/edit/tick/delete, Shopping quantity, and refresh/unseen-state behaviour.
- Local-only lists never appear in the browser because they never leave the device.

Future funding / entitlement design:
- Do not build billing now, but leave the architecture open for it.
- Local-only use should remain free.
- Online sync/sharing/browser access may initially be free while service costs are negligible.
- If meaningful recurring backend cost develops, the preferred model is a small annual fee, notionally around US$5/year, rather than a monthly subscription.
- Voluntary donations/support may also be offered separately from paid feature entitlement.
- Do not hard-wire payment logic into list operations. The sync/backend layer should query an account entitlement such as whether online access is currently permitted.
- Entitlement design should be able to support future states such as free, supporter, paid-online, promotional or admin-granted access without changing list/sync logic.
- Avoid promising that online service will remain unlimited and free forever.
- If funding is ever introduced, existing users should receive reasonable notice/transition rather than abrupt loss of shared data.
- Leave room for operational safeguards such as account/list/member/item limits and backend kill switches, but do not implement them until justified.
- Popularity should degrade safely: local use continues even if online service must be throttled, paused or temporarily disabled.

- Ordinary direct client writes to sensitive membership/list-creation paths were removed in favour of controlled RPC functions.
- Normal item/list reads hide deleted rows; sync uses a controlled snapshot that can return tombstone/removal state so offline clients can learn deletions without weakening normal RLS reads.
- Android dependencies now include supabase-kt 3.2.1 Auth/PostgREST and Ktor Android 3.2.1. `JSimpleListSupabase` is implemented with PostgREST default schema `jsimplelist`.

- Supabase custom SMTP is configured through Resend using the dedicated sender `jsimplelist@jobsheet.com.au`; Proton now has that address. A dedicated restricted Resend sending API key is used only as the Supabase SMTP password.
- Supabase Magic link or OTP email template now sends a six-digit `{{ .Token }}` code, explicitly stating that it is valid for 1 hour and single-use.

Account / ownership decisions:
- Online identities are persistent Supabase Auth users with stable UUIDs; sessions may expire/sign out without deleting the account.
- Local-only use remains account-free. Signing in must never automatically upload existing local lists.
- JSimpleList must provide a transparent `Delete online account` function. Local Room lists on that device are not deleted by online-account deletion.
- Account-deletion wording/semantics: `This permanently removes your JSimpleList online account and shared-list access. Local lists stored on this device are not deleted. Shared lists you own will be destroyed.`
- Ownership transfer is deliberately not required. The creator/owner owns the online shared list; deleting the owner's online account destroys that owner's online shared lists and other members lose access.
- Account deletion itself must be a controlled privileged server-side operation; no admin/secret credential may be shipped to Android.
