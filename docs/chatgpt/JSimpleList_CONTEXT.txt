DESIGN / BEHAVIOUR DECISIONS
----------------------------
- Keep the app deliberately small and local-first.
- Todo item fields: description + completed.
- Shopping item fields: Qty + description + completed.
- Shopping Qty defaults to 1.
- Completed items remain visible so they can be unticked.
- Completed Shopping Qty and description should both show strike-through.
- Pinch resizes content text, not structural UI such as the app title, tabs, Qty / Item headings, Add/Delete text or hint.
- Pinch must work regardless of pinch direction; diagonal pinch is normal.
- Do not use whole-screen transformable handling now that horizontal paging exists.
- Two-finger pinch handling must leave one-finger horizontal pager gestures and vertical list scrolling available.
- Horizontal swiping changes lists; tapping list headings must continue to work as well.
- List headings show incomplete-item counts.
- Future shared-list headings should also be able to show a small red unseen-activity marker/star beside the count.
- Hide the pinch hint once the active list contains 5 or more items.
- Existing items are edited inline.
- Keep list rows compact without making controls fiddly.
- Be greedy with horizontal occupancy on phone screens: avoid unnecessary outer padding and use available width for item text.
- Keep Add and Delete visually secondary to list content.
- Use Manrope throughout the app.
- Use the JSimpleList logo blue/cyan colour family throughout.
- Final package ID is au.com.jobsheet.jsimplelist.
- Visible/public name is JSimpleList.
- Repository is public on GitHub under jobsheet-aus/JSimpleList.
- Google Play is the intended public distribution channel; direct APK distribution from jobsheet.com.au is no longer planned.
- Do not expose an easy direct support-email channel in the app.
- GitHub and jobsheet.com.au are the preferred public information links.

FUTURE SHARED LIST DESIGN
-------------------------
This is a wishlist/future feature and is not implemented yet.

Core decision:
- A shared list should be a list in its own right, not a special shared-items section inside an otherwise private Shopping list.
- Household and business/work examples should use the same underlying model.
- Example household list: "Home Shopping" shared by Josh and Kate.
- Example work list: a fittings/materials list shared by multiple plumbers.

Expected behaviour:
- Local Todo and Shopping must continue to work without login or internet.
- Sharing should be optional and should not force registration on ordinary users.
- Shared lists should remain locally cached/offline-capable and synchronize when connectivity returns.
- Shared-list membership belongs directly to each list initially; do not build a global team/group hierarchy unless it becomes genuinely useful.
- A shared list may have an owner and one or more members.
- When another member adds or changes an item, the user's list heading should show a small red unseen-activity star/marker beside the item count.
- A user's own changes do not create an unseen marker for that user.
- The unseen marker should clear when that user actually views the updated list/page.
- The per-user state should be modelled as something like last_seen_at rather than a single global has_notification flag.
- Initially use the in-app unseen marker rather than Android push notifications.
- Android push notifications may be considered later if they prove worthwhile.
- Shared lists should include a manual refresh/reload action for user confidence and recovery.
- Manual refresh must genuinely query server state and reconcile the local copy.
- On successful manual refresh show a short transient message such as "List refreshed".
- On failure show a concise failure message and retain the local cached list.
- Realtime synchronization should normally happen silently; manual refresh is a user-controlled sanity check.

Possible server/backend direction:
- Supabase/PostgreSQL is the leading candidate because it provides authentication, relational membership, Row Level Security and realtime capabilities without requiring a custom Flask service.
- No final backend choice has been committed yet.
- If sharing is built, authentication should be optional and lightweight; email magic-link/one-time-code style authentication is preferred over forcing another password if practical.
- Likely data concepts: users, lists, list_members, items.
- Server-side authorization must ensure only members of a list can read/change that list.
- A future move from SharedPreferences + JSON to Room may become worthwhile for robust item-level synchronization, but do not refactor persistence merely in anticipation of sharing.

SETTINGS / PREFERENCES PLAN
---------------------------
Do not add a Settings screen merely to expose options that are not genuinely useful.

Current decisions:
- Keep pinch-to-resize text as-is. It works well and does not need a text-size lock/reset setting at present.
- Keep the current opening-list behaviour rather than adding a default-list preference. This should also generalise cleanly when lists become dynamic.
- Keep completed items sorted below incomplete items as normal list behaviour rather than a preference.
- List ordering is the first credible future preference once dynamic list creation exists.
- Likely list-order choices are creation order and alphabetical order.
- Creation order should be the default.
- Manual list ordering may be considered later if there is a real need.

Settings will become more relevant when sharing exists.

Future sharing-related Settings areas, only when sharing exists:

- Sign in / sign out.
- Shared-list invitations.
- Shared-list members.
- Leave list / remove member where permitted.
- Manual refresh/sync controls if not placed directly in the shared-list UI.

Do not add empty Account, Sharing or Groups sections before those features exist.
About remains a separate top-right control.

WORKING STYLE
-------------
- Prefer the smallest practical change.
- Bundle related UI tweaks into as few iterations as practical.
- Build before committing.
- Test important UI behaviour on the real Android phone before committing.
- Use git diff --check before commits.
- Keep unrelated Android Studio / .idea noise out of functional commits.
- deploymentTargetSelector.xml is ignored as local run-target state.
- Avoid Android Studio signing-wizard work where command-line Gradle can do the job.
- Keep signing secrets local and ignored by Git.
- Do not create or replace the permanent signing key casually.
- Current phone test data is disposable during development.
- Current development loop uses the debug APK for faster iteration.
- The release-signed installed app cannot be replaced by a debug-signed APK because Android rejects signature mismatch; uninstalling was acceptable because current phone data was disposable.
- Do not assume an APK installed after a failed Gradle build is the new build: an old APK can remain at the output path. Verify BUILD SUCCESSFUL before install when a build has failed.
