JSimpleList first-class invitation/onboarding design
Updated: 2026-09-02

PURPOSE
-------
This document is the authoritative design reference for JSimpleList invitation, recipient onboarding and sharing-event delivery.

The subsystem spans Android, Supabase Auth, PostgreSQL/RLS/RPCs, Edge Functions, Firebase Cloud Messaging, email templates, jslist.jobsheet.com.au, Android App Links and recipient fallback/error handling.

PRODUCT OBJECTIVE
-----------------
For an existing JSimpleList user, the normal experience should be fast:

Owner sends invitation
-> invitation is committed authoritatively
-> recipient receives an Android push when available
-> tapping the push opens the relevant invitation
-> recipient chooses Decline or Accept
-> Accept imports/reconciles the shared list
-> Decline/Accept notifies the owner through Android push

For a genuinely new user, the email must be a real onboarding/invitation message rather than a generic sign-in email. It must explain what JSimpleList is, why the email arrived, where to get the app, what list/inviter is involved and how any six-digit fallback code is used.

CORE AUTHORITY MODEL
--------------------
Authentication and invitation semantics remain separate.

Supabase Auth owns proof of email identity and authenticated session creation.
JSimpleList owns list sharing, invitation status, membership and list access.

The authoritative product invitation is the row in `jsimplelist.list_invitations`.
A URL, token, list UUID, invitation UUID or push payload alone must never grant list access.

Membership is granted only through:
    jsimplelist.accept_list_invitation(target_invitation_id uuid)

That RPC validates authentication, authenticated email, active invitation, email match and active list before membership is created/reactivated.

Decline is authoritative through:
    jsimplelist.decline_list_invitation(target_invitation_id uuid)

A forwarded link/push must therefore never allow the wrong account to gain membership.

INVITATION LIFECYCLE INVARIANTS
-------------------------------
- A fresh invitation to the same `list_id + lower(trim(invited_email))` supersedes every earlier lifecycle for that exact pair.
- Reinvite removes invitation-derived notifications/outbox rows for the older lifecycles before deleting the old invitation rows, then creates one fresh invitation UUID.
- A person who is already an active member of the list is rejected rather than reinvited.
- Deleting a list cancels outstanding pending invitations.
- Pending-recipient discovery only returns invitations whose list remains active.
- Historical stale/deleted/superseded invitation data was cleaned by migration `20260901091139_purge_superseded_invitation_history.sql`.

CURRENT RECIPIENT UI
--------------------
`get_my_pending_invitations()` returns active pending invitations with list name, list kind and inviter display name.

The Android prompt identifies the inviter/list and explains the list type, then offers `Decline` and `Accept`.

Accepted wording direction:
    You have been invited by <inviter> to join <list name>. This is a <list type> that you can add items to and mark as done.

    Accepting the invitation gives you access to the list.

Decline is not a local dismissal. It calls the server decline RPC and removes the pending action only after successful decline.
Accept calls the acceptance RPC and then reuses `discoverOnlineLists()`; do not create an invitation-specific list-import path.

ONE USER-VISIBLE NOTIFICATION PATH
----------------------------------
JSimpleList deliberately uses one user-visible sharing-notification mechanism:
    FCM -> Android system notification tray

The previous Android `NotificationRepository` / automatic `Sharing update` dialog path was removed because it duplicated the same event after the FCM notification.

The server `notifications` table may remain as durable application-event/source data for the push outbox. It is not a second Android notification UI.

Pending invitation dialogs are different: they are actionable application state discovered from the authoritative invitation table/RPC, not a notification fallback.

If the user denies Android notification permission, JSimpleList accepts that immediate invitation/join/decline alerts may not be visible. Do not reintroduce a second automatic in-app notification system solely to compensate.

PUSH ARCHITECTURE
-----------------
Android uses Firebase Installation IDs (FID), not deprecated FCM token APIs.

`jsimplelist.push_devices` associates:
- authenticated user UUID
- server-derived authenticated email
- persistent client instance UUID
- Firebase Installation ID
- platform/last-seen metadata

Android stores the active push user ID. Incoming sharing pushes must contain `recipient_user_id`; the Firebase service ignores a push when it does not match the currently active account.

Invitation push payload includes invitation/list/inviter context.
Accepted/declined push payloads originate from durable `push_outbox` jobs and include notification ID, recipient user ID, list ID/name and actor display name.

`send-push-outbox` is deployed and proven on real devices. It marks `sent_at` only after successful FCM acceptance and records failed attempts/errors for retry. A fully independent scheduler/worker for stranded retry rows remains future work; current Android accept/decline paths nudge the worker best-effort after the authoritative RPC succeeds.

NOTIFICATION TAP ROUTING - IMPLEMENTED
--------------------------------------
Android notification routing is implemented and real-device tested.

`SharingNotificationManager` includes route context in the PendingIntent:
- event type
- intended `recipient_user_id`
- `list_id`
- `invitation_id` for invitation events

`MainActivity` handles both cold-start and `onNewIntent` routes. Before applying a route it re-checks that the current authenticated Supabase user matches the intended recipient carried by the notification.

Routing behaviour:
- `list_invitation` -> reload authoritative pending invitations and surface the exact matching invitation when it still exists.
- `invitation_accepted` -> open the affected list when that list remains visible/accessible.
- `invitation_declined` -> open the affected list when it remains visible/accessible.
- Invalid/stale/wrong-account routes do not grant or expose access.

Routing extras are navigation context only. They never replace the authoritative invitation/member checks.

RECIPIENT MATURITY / DELIVERY - IMPLEMENTED FOUNDATION
-------------------------------------------------------
Invitation authority and delivery policy are now explicitly separated.

After `replace_list_invitation()` creates the authoritative invitation, deployed `invite-list` calls the server-only classifier:
    jsimplelist.classify_invitation_recipient(target_email)

Classification uses JSimpleList-owned evidence, not raw Auth existence:

1. `ACTIVE_ANDROID`
   - at least one matching registered `push_devices.user_email`
   - strongest evidence the recipient is actively equipped with JSimpleList Android
   - immediate path: push only; no immediate auth/sign-in email

2. `KNOWN_USER`
   - no current matching push device
   - resolved Auth identity has a JSimpleList `profiles` row
   - invitation remains pending/discoverable
   - no immediate duplicate email
   - current delivery foundation schedules a 24-hour reminder due time

3. `GREEN`
   - no JSimpleList profile and no push-device evidence
   - raw `auth.users` history by itself does not make the recipient a known JSimpleList user because bootstrap/invite flows can create Auth rows
   - current transitional implementation still uses ordinary `signInWithOtp()`
   - this branch must be replaced by the purpose-specific onboarding handoff described below

Migration `20260901123652_add_invitation_delivery_foundation.sql` adds:
- the server-only maturity classifier
- `jsimplelist.invitation_delivery`, one row per authoritative invitation where delivery lifecycle state is needed
- immediate channel, push attempt/success timestamps and reminder timing
- cleanup on invitation acceptance/cancellation

`invitation_delivery` is delivery state only and never membership authority.

Cleanup invariants:
- accept -> delivery row deleted in the same invitation-state transition
- decline/cancel -> delivery row deleted
- superseding reinvite -> old invitation hard-delete cascades delivery cleanup
- list deletion -> existing invitation cancellation transition triggers delivery cleanup

Real hosted/device testing proved:
- established recipient classified `ACTIVE_ANDROID`
- immediate channel `PUSH`
- push success recorded
- 24-hour reminder due state created
- no immediate stock sign-in email on the established-user lane
- both Accept and Decline leave zero pending delivery rows for the resolved test invitation

The direct invitation push is still sent synchronously by `invite-list`. Removing the unnecessary Auth-email wait materially improves the established-user path, but push should later move behind durable/non-blocking delivery so sender success is not coupled to Firebase work.

NEW-USER EMAIL REQUIREMENTS
---------------------------
The purpose-specific email must include:
- a subject that communicates a JSimpleList invitation rather than merely a sign-in code
- inviter display name
- list name
- a short explanation of JSimpleList
- a clear `Open shared list` action where appropriate
- a clear `Get JSimpleList` / Google Play path for a person who does not yet have the app
- JSimpleList landing-page information
- safe ignore wording
- expiry/use-once guidance where relevant to the Auth primitive
- if a six-digit fallback code is included: explicitly say `enter this code in the JSimpleList app`

A new recipient must not be expected to already know where JSimpleList comes from or what a six-digit code is for.

GREEN ONBOARDING HANDOFF - TARGET
---------------------------------
A genuinely new recipient may know nothing about JSimpleList and may not have the app installed. The target common path is one obvious invitation action that carries that person through installation/authentication and into the shared list with minimal typing.

Required architecture:
- create a short-lived, single-use, opaque server-side handoff identifier tied to invitation/bootstrap state
- the opaque handoff may be carried through browser/App-Link/install continuation
- never put a raw Auth secret/token in a Google Play referrer
- possession of the handoff identifier itself never grants list membership
- the recipient must authenticate/verify control of the invited email
- final membership still occurs only through `accept_list_invitation(target_invitation_id)`
- after authentication/acceptance, normal discovery/reconciliation imports the list and the app opens it
- first successful JSimpleList entry establishes normal profile/device evidence so future invitations can classify the person as established

The green journey must handle:
1. App already installed -> verified Android App Link opens JSimpleList with the handoff.
2. App not installed -> invitation website explains JSimpleList, routes to Google Play and preserves only the opaque continuation identifier through an appropriate install-continuation mechanism.
3. Desktop/browser -> safe explanatory/browser handoff rather than assuming an Android app is present.
4. Wrong account -> do not accept; guide authentication as the invited email without leaking shared content.
5. Forwarded link -> authentication/email validation still prevents membership by the wrong person.
6. Expired/consumed/resolved handoff -> show a safe terminal/recovery state.
7. Invitation accepted/declined/superseded/list deleted -> pending handoff/reminder/delivery server state must be removed immediately.

Display-name creation must not become unnecessary onboarding friction. A reasonable provisional fallback may be used and remain editable later if that is the cleanest path.

WEBSITE / APP-LINK HANDOFF
--------------------------
The existing first-class handoff infrastructure is deployed and useful:
- scanner-safe invitation page on `jslist.jobsheet.com.au`
- auth callback route under `jslist.jobsheet.com.au/auth/invite`
- verified Android App Links for debug testing
- browser handoff can present Open JSimpleList / installation guidance

The GREEN implementation should inspect and reuse this infrastructure rather than creating a parallel invitation website.

The handoff page must preserve safe behaviour for:
- app installed
- app not installed
- desktop/browser
- wrong account
- expired/consumed auth state
- forwarded link

AUTH EMAIL / TEMPLATE POSITION
------------------------------
Ordinary JSimpleList sign-in should remain an ordinary passwordless authentication email.
Do not distort the normal sign-in template just to make product invitations read correctly.

The current invitation path incorrectly reuses that ordinary sign-in flow for every invite, which is why the subject/body are not ideal.
The next implementation should separate genuine new-user onboarding email from ordinary sign-in email and known-user push delivery.

SERVER EVENT / OUTBOX MODEL
---------------------------
Persistent server events cover invitation accepted/declined and feed `push_outbox` transactionally.
Push failure must never roll back invitation accept/decline.

Invitation delivery now also has explicit server-only `invitation_delivery` state. This is transient delivery/reminder/handoff lifecycle state attached to an authoritative invitation, not a second invitation authority.

Invitation creation currently sends the ACTIVE_ANDROID FCM push directly from `invite-list`. This is proven but still synchronous. A later refinement should enqueue the immediate invitation push durably so the sender can return after authoritative invitation/delivery-state creation rather than waiting on Firebase.

The delayed-reminder worker/job is not yet implemented. When implemented, it must act only on still-current due delivery state and naturally do nothing after accept/decline/reinvite/list-deletion cleanup.

DECLINE / ACCEPT WORDING
------------------------
Invitation push:
    <inviter> invited you to join <list>

Accepted push to inviter:
    <actor> joined <list>

Declined push to inviter:
    <actor> declined your invitation to <list>

Use `join`, not `share`, for the recipient-facing invitation action because the recipient is being granted access to somebody else's list rather than being asked to expose their own list.

FAILURE / EDGE CASE MATRIX
--------------------------
The final workflow must handle at least:
1. Existing user, app installed, push permitted
2. Existing user, app installed, Android notifications denied
3. Existing user with stale/no registered push device
4. New user, app not installed
5. New user opens email on desktop
6. Recipient already signed in as invited account
7. Recipient signed in as a different account
8. Invitation link/push forwarded
9. Authentication state expired or already consumed
10. Invitation declined
11. Invitation accepted
12. Invitation superseded by a reinvite
13. Invitation cancelled because list was deleted
14. Recipient already an active member
15. Recipient previously removed and reinvited
16. Multiple pending invitations to different lists
17. Network failure during invitation creation
18. Network failure during push/email delivery
19. Network failure during acceptance/decline
20. Delayed reminder becomes due after invitation has already been accepted/declined/superseded/deleted
21. Notification tapped after invitation/list is no longer valid
22. Notification tapped while wrong account is active

UX PRINCIPLES
-------------
- Prefer one obvious path, not duplicated notification mechanisms.
- Existing-user invitation should feel immediate.
- Do not make a known user wait for an unnecessary auth email.
- Do not ask for the same email repeatedly.
- Do not expose raw UUIDs/tokens/backend terms.
- Do not treat FCM acceptance as proof that Android displayed the notification.
- A technically successful backend call is not proof that recipient UX is complete.
- Preserve simple fallback/recovery without making the common path complicated.

IMMEDIATE NEXT SESSION
----------------------
Begin with the GREEN recipient onboarding handoff.

Implementation order:
1. Inspect the existing `jslist.jobsheet.com.au` invitation/auth routes, Android App Link intent handling and currently available Supabase Auth bootstrap primitives before choosing the exact mechanism.
2. Define the opaque short-lived single-use handoff record and its cleanup/expiry semantics. The handoff must reference invitation/bootstrap state without itself granting membership.
3. Implement the purpose-specific GREEN invitation email: inviter, list, short JSimpleList explanation, one Open shared list action, Get JSimpleList/Play guidance, safe-ignore wording and explicit fallback-code instructions only if a code remains part of the chosen Auth primitive.
4. Reuse the existing website/App-Link infrastructure for installed-app and browser paths; add an install-continuation mechanism that preserves only the opaque handoff identifier.
5. Implement Android resume/onboarding so the invited email is authenticated/verified, any required provisional profile is established without needless friction, `accept_list_invitation()` grants membership, normal discovery imports the list and the app opens it.
6. Prove wrong-account, forwarded, expired, already-resolved and app-not-installed cases.
7. Prove the complete never-used-JSimpleList -> install -> authenticate -> accept -> imported/open shared list journey on a real device.
8. Replace/remove the transitional GREEN `signInWithOtp()` invitation branch once the purpose-built path is proven.
9. Then implement the 24-hour still-pending reminder worker for established recipients and move immediate invitation push behind a durable/non-blocking delivery path.
10. Re-run the focused sharing regression before moving on to unrelated sharing UX.

Do not weaken the authority boundary: the invitation row + authenticated-email validation in `accept_list_invitation()` remain the only path to membership.
