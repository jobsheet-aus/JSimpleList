JSimpleList first-class invitation/onboarding design
Updated: 2026-08-30

PURPOSE
-------
This document is the authoritative design reference for JSimpleList invitation and recipient onboarding.

The invitation workflow is product-critical. It spans:
- Android
- Supabase Auth
- PostgreSQL/RLS
- Supabase Edge Functions
- email templates
- jslist.jobsheet.com.au
- Android App Links
- recipient fallback/error handling

Detailed invitation architecture belongs here rather than being duplicated throughout JSimpleList_CONTEXT.txt.

PRODUCT OBJECTIVE
-----------------
The preferred recipient experience is:

Owner sends invitation
→ recipient receives one useful email
→ recipient taps Open shared list
→ JSimpleList opens authenticated
→ pending invitation is shown
→ recipient taps Accept
→ shared list appears

The user should not normally need to:
- manually re-enter the invited email address
- manually request another authentication email
- understand Supabase terminology
- copy a six-digit code unless the one-tap path cannot be used
- understand list UUIDs, invitation IDs or authentication tokens

Manual OTP remains a fallback rather than the preferred invitation path.

CORE AUTHORITY MODEL
--------------------
Authentication and invitation semantics are deliberately separate.

Supabase Auth owns:
- proof that the user controls an email address
- passwordless authentication tokens/codes
- authenticated session creation and persistence

JSimpleList owns:
- which list has been shared
- who was invited
- whether the invitation is pending/accepted/cancelled
- membership
- list access

The authoritative product invitation is the row in:
    jsimplelist.list_invitations

A URL, token, list UUID or invitation UUID alone must never grant list access.

Membership is granted only through the controlled acceptance path:
    jsimplelist.accept_list_invitation(target_invitation_id uuid)

That RPC verifies:
- the caller is authenticated
- the authenticated email exists
- the invitation is still active
- the invited email matches the authenticated email
- the target list is still active

Only then does it create/reactivate membership and mark the invitation accepted.

A forwarded invitation link must therefore not allow another account to gain access.

ONE AUTHENTICATION PATH
-----------------------
JSimpleList deliberately uses the normal Supabase passwordless email authentication flow for invitation recipients.

Do not use Supabase Auth's special Invite-user authentication flow as the JSimpleList product invitation mechanism.

Reason:
- JSimpleList already has its own invitation model
- normal OTP/magic-link authentication is sufficient to prove email ownership
- one authentication path reduces recipient friction and Android verification complexity
- the same path works for existing and newly created Auth users
- the invitation database row, not Supabase Auth invitation state, determines product access

The existing owner-side invite Edge Function:
    supabase/functions/invite-list/index.ts

currently:
1. authenticates the owner
2. verifies list ownership
3. creates or reuses an active list_invitations row
4. requests a normal Supabase passwordless sign-in for the invited email

The direct Resend invitation-email implementation has been removed from this function.

EMAIL STRATEGY
--------------
Supabase Auth remains responsible for authentication-email generation and delivery through the configured Resend SMTP service.

Normal passwordless email should provide:
- JSimpleList identity/branding
- a one-time authentication mechanism
- expiry/use-once information
- a safe ignore message
- useful JSimpleList links

The desired invitation email ultimately provides both:
- primary one-click Open shared list flow
- six-digit OTP fallback

Useful links include:
- Learn about JSimpleList:
  https://www.jobsheet.com.au/jslist
- Get JSimpleList on Google Play:
  https://play.google.com/store/apps/details?id=au.com.jobsheet.jsimplelist

Do not rely on direct Resend API calls from Android or browser code.
Do not expose Resend API secrets to clients.

FIRST-CLASS HANDOFF DESIGN
--------------------------
Preferred transport:

Invitation email
→ HTTPS handoff on jslist.jobsheet.com.au
→ deliberate user action
→ Android verified App Link when available
→ JSimpleList Android app
→ Supabase authentication completion
→ pending invitation discovery
→ Accept
→ shared list import

The website is deliberately involved rather than sending a raw one-time authentication link directly to the Android app.

Reasons:
- gives JSimpleList one stable branded public URL
- supports installed and not-installed recipients
- supports desktop recipients
- provides a natural future browser-client path
- reduces risk from email security scanners/prefetchers consuming a one-time authentication action before the user deliberately acts
- allows fallback guidance without exposing backend concepts

WEBSITE HANDOFF STATES
----------------------
The handoff page should support these states deliberately.

App installed:
- show Open JSimpleList
- verified Android App Link opens the app

App not installed:
- explain that the user was invited to JSimpleList
- offer Get JSimpleList on Google Play
- preserve enough safe state for the user to continue after installation where practical
- OTP remains available as fallback

Desktop/browser:
- explain the invitation
- offer browser use when that path is production-ready
- otherwise offer the landing page and Android installation path
- do not present an unfinished browser client as a complete product

Browser client ready:
- offer Use JSimpleList in browser
- browser must use the same Supabase identity, memberships and RLS
- browser is another client, not a separate invitation authority

ANDROID APP LINK
----------------
Preferred public link form should use HTTPS on the controlled JSimpleList domain, for example:

    https://jslist.jobsheet.com.au/...

rather than making a custom URI such as:

    jsimplelist://...

the primary public entry point.

Android verified App Links are preferred because they:
- use a normal branded HTTPS URL
- can open JSimpleList directly when installed
- retain meaningful browser behaviour when not installed
- are appropriate for a public Play Store product

Implementation will require deliberate inspection/design of:
- AndroidManifest intent filters
- domain verification
- .well-known/assetlinks.json
- signing certificate fingerprints
- web route behaviour
- Android intent handling
- Supabase auth callback/state handling

Do not implement these piecemeal before the exact URL and state contract is documented.

TOKEN / URL SECURITY
--------------------
Do not invent a custom authentication token when Supabase provides the required authentication primitive.

The web/app handoff may carry:
- Supabase authentication state/token material
- an invitation identifier as non-authoritative context
- safe UI/navigation context

But none of those values alone grants membership.

Access authority remains:
authenticated Supabase identity
+
pending invitation visible/valid for that identity
+
successful accept_list_invitation()

If a link is forwarded:
- the forwarded recipient must not gain the shared list
- the original invited email remains authoritative
- an authenticated wrong account must receive a safe mismatch/error experience

PENDING INVITATION CLIENT FLOW
------------------------------
Android currently has recipient-side foundation:

InvitationRepository.kt:
- sendInvitation()
- loadPendingInvitations()
- acceptInvitation()

MainActivity.kt:
- loads pending invitations after restored-session startup
- loads pending invitations after fresh sign-in
- displays a List invitation dialog
- Accept calls accept_list_invitation()
- then reuses discoverOnlineLists()
- accepted membership imports as ONLINE_MEMBER
- Not now dismisses the prompt locally without cancelling the server invitation

This code builds successfully as of 2026-08-30.

The current recipient UI is functional foundation, not the final first-class onboarding experience.

ONLINE MEMBER IMPORT
--------------------
Existing ListSyncRepository.discoverOnlineLists() remains the canonical post-acceptance import/reconciliation path.

The accepted invitation creates/reactivates list_members.

get_my_online_lists() then returns the shared list with role:
    member

Android maps:
    member -> ONLINE_MEMBER

The list is imported/refreshed through the existing online-list cache/snapshot machinery.

Do not create a separate invitation-specific list import path.

CURRENT OWNER-SIDE FLOW
-----------------------
Current Android Share list behaviour includes:
- New list moved into hamburger
- prominent current-list action is Share list
- local list can be made available online for the current account
- online list can invite someone by email
- Send invitation calls InvitationRepository.sendInvitation()
- invite-list Edge Function creates/reuses a pending invitation and triggers normal Supabase passwordless auth email

The Share list UI currently has two intentions:
1. use this list on my other devices
2. invite someone

Do not expose the term self-share to users.

CURRENT HOSTED BACKEND STATE
----------------------------
Relevant migrations:
- 001-024 existing JSimpleList backend
- 025_unique_active_list_invitation.sql

Migration 025 is applied to the hosted Supabase project.

Its purpose is to prevent duplicate simultaneous active invitations for the same list/email pair.

Relevant existing RPC:
    accept_list_invitation(target_invitation_id uuid)

Relevant existing discovery RPC:
    get_my_online_lists()

Relevant deployed Edge Functions:
    delete-account
    invite-list

invite-list is currently deployed using normal signInWithOtp() rather than direct Resend API email sending.

EMAIL / RESEND STATE
--------------------
JSimpleList Auth email delivery uses Supabase Auth with Resend SMTP.

A new Resend key was created on 2026-08-30 and:
- stored locally in git-ignored D:\SimpleList\invite-secrets.env
- configured in Supabase Auth SMTP
- configured as Supabase Edge Function secret RESEND_API_KEY

The current invite-list implementation no longer needs RESEND_API_KEY directly, but the secret may remain configured until deliberate cleanup.

Do not commit invite-secrets.env.

The local ignore rule was verified with:
    git check-ignore -v invite-secrets.env

A direct Resend invitation email sent during development was accepted by Gmail and eventually appeared in Spam. This was an inbox-placement issue, not an API-authentication failure.

The subsequent Supabase OTP invitation email arrived promptly after the recipient marked the sender as Not spam.

EMAIL TEMPLATE POSITION
-----------------------
Normal Magic link or OTP template:
- remains the ordinary JSimpleList authentication email
- currently uses the six-digit {{ .Token }} path
- includes the JSimpleList landing-page and Play Store links

Invite user template:
- was updated to contain the intended JSimpleList invitation wording and OTP information
- is not intended to be the primary JSimpleList product invitation mechanism

JSimpleList currently intends to use only the normal passwordless authentication path for actual invitation onboarding.

Before changing templates again, inspect their current Supabase state and the exact token/link requirements for the first-class handoff.

FAILURE / EDGE CASE MATRIX
--------------------------
The final workflow must deliberately handle at least:

1. App installed, recipient not signed in
2. App installed, recipient already signed in as invited account
3. App installed, recipient signed in as different account
4. App not installed
5. Recipient opens invitation on desktop
6. Browser client available
7. Browser client unavailable/incomplete
8. Invitation link forwarded
9. Authentication token expired
10. Authentication token already consumed
11. Invitation cancelled
12. List deleted
13. Recipient already a member
14. Recipient previously removed and reinvited
15. Multiple pending invitations
16. Recipient chooses Not now
17. OTP fallback
18. Email scanner/prefetch behaviour
19. Network failure during authentication completion
20. Network failure during invitation acceptance
21. Android app opens without valid pending invitation
22. User installs app after originally opening the invitation link

Each case should have a defined safe user-visible result before release.

UX PRINCIPLES
-------------
The invitation flow should feel like a product feature rather than infrastructure.

Prefer:
- one useful email
- one obvious primary action
- branded URLs
- minimal typing
- explicit but short explanations
- safe recovery paths
- no backend terminology
- no unexplained authentication transitions

Avoid:
- forcing users to understand OTP versus invitation concepts
- asking for the same email repeatedly
- sending multiple emails when one can do the job
- exposing raw UUIDs/tokens
- making a user request another OTP after already receiving an invitation
- depending on an unfinished browser client
- treating a technically successful backend call as proof that the recipient UX is complete

IMPLEMENTATION BOUNDARIES
-------------------------
Work through this subsystem deliberately:

1. Architecture and URL/auth-state design
   - inspect current web hosting/routes
   - inspect Android manifest/deep-link handling
   - inspect current Supabase redirect/auth settings
   - determine exact token-hash/magic-link/OTP fallback contract
   - specify exact public URLs and authority boundaries before coding

2. Website handoff
   - implement safe branded handoff page/route
   - handle installed/not-installed/browser states
   - avoid consuming one-time auth state through automated scanning

3. Android verified App Link handling
   - configure manifest
   - configure assetlinks.json
   - verify release/debug signing implications
   - route incoming handoff into controlled auth completion

4. Supabase authentication completion
   - establish authenticated session safely
   - preserve the existing ordinary OTP fallback
   - handle wrong-account and expired-token states clearly

5. Pending invitation acceptance/import
   - integrate with the existing PendingInvitation foundation
   - preserve accept_list_invitation() as membership authority
   - reuse discoverOnlineLists()

6. Fallback/error states
   - implement the documented edge-case matrix
   - ensure forwarded/expired/invalid links remain safe

7. End-to-end validation and UX polish
   - real sender phone
   - real recipient phone
   - fresh install
   - existing install
   - desktop/browser
   - wrong account
   - expired/invalid link
   - Play Store installation path
   - normal OTP fallback
